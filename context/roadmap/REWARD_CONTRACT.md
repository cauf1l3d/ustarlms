# Контракт награды за точку маршрута

Статус: **требование владельца принято; техническая спецификация для R04–R06, ещё не реализована и не опубликована как production policy**. Тарифы ниже — предложение для пилота. Текущие ADR-0003/0004 и ledger остаются обязательными.

## Пользовательский результат

У каждой публикуемой учебной точки есть проверяемое условие и положительная награда. Сотрудник видит их до начала. После нового подтверждённого прохождения он видит завершение, начисленные XP/USCOIN, продвижение к достижению и следующую точку. Результат сохраняется после refresh и отображается в кошельке/достижениях. Получение технического completion без награды или анимация без сохранённого начисления не закрывают требование.

Предлагаемый стартовый тариф: **10 XP + 1 USCOIN за новое подтверждённое прохождение точки**. Одинаковый базовый тариф упрощает пилот; bonus за маршрут/аттестацию можно добавить отдельным правилом. Размер, дата начала и владелец rule version фиксируются до включения начислений. Старая формула dashboard не должна дополнительно начислять за тот же факт скрытым вторым способом.

## Разделение смыслов

| Величина | Смысл | Источник |
|---|---|---|
| Учебный факт | Что действительно выполнено, каким способом и когда | Существующие Moodle/USTAR providers → canonical evidence по ADR-0003 |
| Право на награду | Одно новое eligible прохождение по версии правила | Стабильная серверная identity completion/цикла, привязанная к факту |
| XP | Рост/уровень | Проверяемая история XP grants; старое XP сохраняется через документированный переход |
| USCOIN | Расходуемый внутренний баланс | `coin_ledger`; `coin_balance` — существующая производная проекция |
| Achievement | Выполненный критерий: первая точка, маршрут, аттестация | Действительные факты и versioned criteria; уникальная выдача |
| Competition points | Сравнение внутри конкретного сезона | `comp_score_events` по опубликованному rule version и participant snapshot |

Не связывать место в соревновании с остатком кошелька. Не выдавать награду на основании клиентского `amount`, `userid`, `completed=true` или открытия карточки руководителем.

## Единый серверный сценарий

1. Вход получает событие/результат существующего провайдера либо выполняет reconciliation для конкретного сотрудника и доступной точки.
2. Resolver выбирает фактическую точку, parent/override, опубликованную версию и applicability. Проверяются права, account type, последовательность и блокировки адаптации.
3. Evaluator проверяет все обязательные требования. Assessment state «завершено без доказанного pass» не считается успешной аттестацией. Для психометрического профиля награда за заполнение, а не за «желательный» ответ или психологический тип; приватные ответы не идут в leaderboard.
4. Явная команда фиксирует completion-факт и entitlement в согласованной транзакции под блокировкой. Использовать существующий `target_core::record_evidence` через разрешённый use case; не открывать его как универсальный доверенный endpoint для внешнего клиента.
5. На grant применяется зафиксированная rule version. `economy::post` получает стабильный ключ и source reference; новые XP-grants имеют такой же принцип уникальности. Для асинхронных эффектов durable delivery/retry создаётся в той же транзакции, не после её успешного завершения.
6. Ответ содержит только фактический результат `awarded / already_awarded / pending`, сумму и ссылку на историю. После retry недостающий эффект восстанавливается с исходным ключом.

Не вводить отдельный брокер сообщений для этого первого сценария. Если асинхронность нужна, достаточно согласованной durable-записи и Moodle task; сначала проверить возможность повторно обработать существующий факт. Все proposed новые классы/таблицы описываются миграцией/ADR, а не объявляются существующими.

## Identity, версии и повторное обучение

Сейчас progress уникален по `userid + pointid + versionid`. Этого недостаточно, чтобы отличить реальное повторное прохождение одной версии после expiry от повторного запроса. Перед реализацией R05 нужно закрепить стабильную identity:

- `logical_point` связывает родительскую точку и её допустимый override согласно ADR-0004;
- `completion_cycle` выдаётся сервером для нового реального обучения; timestamp HTTP-запроса или случайный request UUID не являются новой попыткой;
- `evidence_id`/версия источника/попытка доказывают выполнение после cutoff этого цикла;
- уникальное entitlement ограничивает одно награждение пользователя за этот logical point и цикл; rule version хранится как provenance, изменение rule само по себе не создаёт новое entitlement;
- published route version, evidence refs, tariff version, earned_at сохраняются и не переписываются при редактировании контента.

Существующий progress и его историю не удалять и не пересоздавать. Способ хранения нового цикла — отдельный design пункт R04/R05 с XMLDB upgrade и тестом миграции. Backfill старых completion — отдельная явно именованная миграция после dry-run; запуск новой версии не должен массово выдать награды за годы истории.

| Событие | Новая награда? |
|---|---|
| Первое фактическое выполнение всех требований доступной точки | Да |
| Несколько вкладок/повтор callback/refresh для того же completion | Нет второй; вернуть существующий результат |
| Перенос старого completion по renewal `keep` | Нет: это тот же заработанный результат |
| Изменение заголовка/тарифа/новая версия без нового обучения | Нет |
| Новое подтверждённое прохождение после принудительного переобучения/expiry | Да, один раз за новый серверный цикл |
| Непройденный, locked, draft или неподтверждённый scope | Нет |
| Просмотр управленческого snapshot или view-as | Не создаёт completion/grant |
| Подтверждённая конечная точка/gate | Да за новое прохождение по её правилу; не означает автоматически выдачу внешнего допуска |
| Необязательный информационный ресурс без действия | Не должен публиковаться как автоматически награждаемая учебная точка; в студии выбрать проверяемое условие |

## Матрица провайдеров

| Тип | Доказательство | Обязательная проверка |
|---|---|---|
| Moodle course | Course completion для нужного сотрудника/курса | Повтор observer и reconciliation дают одну награду |
| Moodle Page/activity | Настроенный completion/viewed только если это условие опубликовано | Открытие соседней/заблокированной точки не засчитывается |
| SCORM | Валидный completion/pass для нужного SCO/попытки | Failed/incomplete и старая попытка после cutoff не закрывают пересдачу |
| Quiz/роль-тест | Проверенный pass и завершённая необходимая ручная оценка | Fail, ungraded и pending не награждаются как успешная аттестация |
| USTAR content open/ack | Route-scoped opened/studied event с нужными версиями | Direct URL вне доступной точки и неподтверждённое ack не достаточны |
| Skill/evidence | Выполнены действующие обязательные правила | Unsupported/expired/revoked facts не проходят |
| Development/team profile | Успешно отправленный профиль по его опубликованному условию | Награда не зависит от приватного результата профилирования |
| Previous steps/gate | Подтверждённые предыдущие шаги и собственная опубликованная политика | Auto-projection не повторяет grant; отсутствие требований — publish error |

Матрица расширяется только для реально поддерживаемых типов. Ни один активный тип точки нельзя оставить без определённого reward-path и назвать поставку завершённой.

## UX и достижения первой поставки

- На точке: условие завершения, размер награды, состояние «получено» и «нужно пройти повторно».
- После прохождения: компактная карточка «Точка пройдена · +10 XP · +1 USCOIN» по фактическому grant; кнопка следующего действия. Пока worker обрабатывает — честное состояние «Награда начисляется».
- Wallet показывает источник/дату/сумму и стабильную ссылку на начисление без выдачи чужой истории.
- Achievements v1: «Первая точка», «Маршрут завершён», «Аттестация пройдена». У каждого criteria version, awarded_at, evidence reference; выдача не зависит от наличия картинки на странице.
- Использовать Moodle badges там, где их критерии подходят; не создавать параллельную систему значков без ADR. Проверить загрузку badge API и существующие выданные badges.
- Reduced-motion отключает анимации; сообщения доступны screen reader; информация не выражается только цветом; desktop/mobile и возврат Back проверяются.

## Приёмка R04–R06

Проверить DB integration и пользовательский smoke:

1. Все строки матрицы: eligible завершение создаёт один факт, один grant каждого обещанного вида и видимый результат.
2. 20 конкурентных доставок одного события: 1 entitlement, 1 USCOIN запись, 1 XP grant, корректный баланс.
3. Сбой после сохранения completion, до/после ledger и перед UI response: retry восстанавливает результат без потерь/дублей. Запись claim не остаётся навсегда «обработано» без награды.
4. Keep/inherited, новая версия без обучения, dashboard GET, view-as, test/service account: нет ложных новых наград.
5. Expiry и реальная повторная попытка той же версии: один новый cycle grant, прежняя история на месте.
6. Неверный amount/userid/pointid и чужой scope не обходят серверную проверку.
7. Ledger sum = projection; insufficient funds и reversal из текущей economy по-прежнему проходят.
8. До/после перехода исторические XP и USCOIN не исчезают и не удваиваются. Откат кода не удаляет grants; отмена ошибочной награды имеет отдельную утверждённую политику, не SQL DELETE.
9. Скриншоты и persisted state для employee, manager, HR подтверждают один результат; badges не выданы повторно.
