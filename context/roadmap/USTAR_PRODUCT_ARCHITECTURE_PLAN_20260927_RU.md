## 2. Архитектурные правила

### 2.1. Один модульный продукт

Сохраняем Moodle-native модульный монолит: прикладные сервисы внутри `moodle/local/ustar`, представления и тема в `moodle/theme/ustar`. «Сервис задач» и «Лента» — продуктовые разделы этой академии; отдельные сетевые микросервисы, новые базы, брокер и второй frontend для них не нужны. Moodle core не меняем.

Страница, API и CLI вызывают одну прикладную команду или запрос. Контроллер разбирает ввод, проверяет сессию, вызывает сервис и отдаёт представление. Тема получает готовые данные навигации и не вычисляет кадровые полномочия. `native_data → external::execute → JSON decode` постепенно заменяется на вызов того же прикладного сервиса, который использует external-адаптер.

| Данные | Единственный владелец | Ограничение |
|---|---|---|
| Аккаунт, пароль, файлы | Moodle user/auth и File API | Не копировать секреты или бинарные вложения в USTAR JSON |
| Допуск к академии | `accounts`, `local_ustar_employment` | Pending, suspended, terminated не получают доступ через новый раздел |
| Должность человека | `organization_identity`, действующие PRIMARY/ACTING назначения | Профиль — совместимая проекция, не второй редактор истины |
| Подразделения и должности | Существующий оргдомен; управляемая миграция по ADR-0002 | Лента и грейды используют стабильные ID, не создают собственную оргструктуру |
| Стандарт, маршрут и evidence | `standard_model`, `route_model`, `route_scope`, канонические evidence | Не выводить квалификацию из пустой матрицы или одной самоотметки |
| Грейд человека | `grade_promotion`, `local_ustar_employee_grades` | Не смешивать личный грейд, должность, уровень навыка и учебный прогресс |
| Задача и блокнот | `learning_tasks`, существующие таблицы задач/событий | Чек-лист остаётся своим типом рабочего процесса; не копировать его ответы в новую задачу |
| Уведомления | Существующий inbox + единый outbox | Сохранённое сообщение и доставленное сообщение имеют разные статусы |
| Социальная публикация | Новый модуль feed в `local_ustar` | Публикации не становятся учебными материалами и не начисляют XP/USCOIN |

### 2.2. Общий контракт изменения

Каждая команда получает реального actor, целевой объект, проверенную область, ожидаемую ревизию и ключ повторяемости, где возможен повтор запроса. На сервере обязательны capability + scope + статус занятости; для записи — POST, sesskey, запрет `view_as`, валидация и транзакция. Видимость кнопки не заменяет проверку.

Блокировки берутся в документированном порядке. Публичная команда владеет блокировкой; внутренний метод, вызываемый из уже заблокированной команды, повторно её не захватывает. Бизнес-факт, аудит и outbox фиксируются согласованно; внешняя доставка выполняется после commit. Чтение страницы не создаёт зачисление, грейд, награду или прохождение.

История сохраняет версию требований, автора решения, время и основание. Исправление оформляется отдельным событием, а не переписыванием прошлого. Для больших миграций — dry-run, пакетная обработка, контрольная точка и отчёт конфликтов; никаких массовых автоматических подтверждений сотрудников, повышения грейдов или пересчёта наград.

### 2.3. Единый интерфейс

Опора — существующие `scss/_tokens.scss`, `_foundation.scss`, `_shell.scss`, `_product_parity.scss` и активная тема. На снимках рабочая академия светлая с мятно-голубыми акцентами, авторизация имеет собственный брендовый блок. Не заменять весь продукт золотой или иной новой палитрой.

Общие компоненты: компактный заголовок, вкладки, toolbar, карточка/строка списка, статус, пустое состояние с следующим действием, поле с ошибкой, подтверждение опасного действия, пагинация, файл-вложение. Mustache/renderer — одна реализация компонента. Локальные CSS описывают раскладку, общие токены — цвет, шрифт, интервалы, радиусы, focus и кнопки. Удаляем пересекающиеся правила только после переноса всех потребителей.

На рабочем экране одна основная кнопка по контексту, вторичные действия рядом с объектом. Редкие настройки раскрываются по запросу. Вместо огромных повторных hero, пустых колонок и технических дисклеймеров — рабочие данные и понятный следующий шаг. Все видимые подписи по-русски; внутренние eventtype/ID остаются в диагностике. Состояния «не настроено», «не назначено», «нет данных», «нет доступа», «ошибка» различаются.

Клавиатура, связанные label, видимый focus, ошибки у поля, контраст, длинные названия, загрузка и повтор запроса входят в приёмку. Контрольные ширины: 360, 768, 1280, 1920 px. Декоративные иллюстрации не переделываем. Макет входа и регистрации сохраняет исходный рисунок/маскота, порядок и содержание; исправляем выравнивание и раскладку формы.

## 3. Восемь приоритетных доработок

### N01. Удалить «Оргпространство» как самостоятельный экран

**Сейчас:** `workspace.php` показывает отдельное полотно подразделений. Ссылка присутствует в `operations.php` и в классификаторах/заголовках `theme/ustar/layout/ustar.php`; это дублирует существующие команду и оргструктуру.

**Как сделать:**

1. Удалить пункт «Оргпространство» из меню, HR-обзора и внутренних ссылок. Основной путь: «Команда» → существующая оргструктура; создание и настройка подразделений остаются в `organization_settings.php` по правам.
2. `workspace.php` оставить только как совместимый GET-переход на канонический экран команды/структуры после проверки доступа. Допустимый поиск перенести явным параметром; неизвестные параметры не копировать. Не принимать mutations через старый вход.
3. Удалить специфичные template/JS/CSS только после поиска всех потребителей. Одноимённый API `get_workspace` и bootstrap другого frontend не удалять по совпадению названия: сначала проверить контракт и заменить его потребителей, если они действительно относятся к удаляемой странице.
4. Обновить breadcrumbs, поиск, home shortcuts, документацию и карту feature → entrypoint. Перенаправление не должно показывать команду человеку без соответствующего scope.

**Где:** `workspace.php`, `operations.php`, шаблоны операций/workspace, `classes/ui.php`, `classes/communication.php` при наличии ссылок, `theme/ustar/layout/ustar.php`; полный поиск URL по `moodle/` и `frontend/`.

**Приёмка:** отдельного полотна и пункта меню нет; старый bookmark приводит к рабочему существующему разделу; структура, сотрудники и управление подразделениями доступны как прежде; никаких новых таблиц.

### N02. Полный контур грейдов

**Сейчас:** `career_grades::catalogue()` читает `data/consultant_grades.json`; привязка должности хранится в `careergrade_<positionid>` с legacy name-based fallback. `grade_rules` уже публикует неизменяемые правила переходов с точными версиями точек, `grade_promotion` создаёт заявки/решения, есть `employee_grades`. Полноценного редактора лестниц нет; экран может закончиться красным сообщением «лестница не настроена».

**Продуктовый контракт:**

- Лестница определяет ступени и правила перехода; должность связывается с опубликованной версией лестницы. Личный грейд принадлежит сотруднику. Назначение должности само по себе не повышает грейд, завершение обучения лишь даёт право запросить переход.
- Рабочие вкладки: «Мой грейд» — текущая ступень, следующий шаг, требования и история; «Заявки команды» — доступные решения; «Настройка» — только уполномоченным; «Назначения» — HR-контроль по людям/должностям и исключениям.
- Контур настройки: создать лестницу → задать ступени и названия → связать с должностями → выбрать подтверждаемые требования каждого перехода → проверить влияние → опубликовать → видеть охват, ненастроенные связи и заявки.
- Стартовая ступень назначается явным доменным действием при включении лестницы для сотрудника; чтение не пишет БД. HR может внести начальный подтверждённый грейд или коррекцию только отдельным полномочием с причиной и историей; это не обход обычного согласования руководителем.
- Заявка фиксирует лестницу, правило, версии evidence/точек и должность на момент подачи. Решение перепроверяет действующего руководителя, применимость и evidence. Перевод человека, отзыв evidence или смена правил дают понятный статус пересмотра; заявка не одобряется молча по новому набору требований.
- При переводе на другую должность внутри той же лестницы перенос грейда допускается по опубликованной политике; для другой лестницы нужна явная таблица соответствий или HR-решение. История не теряется, автоматического повышения нет.
- Архив лестницы запрещает новые привязки, но сохраняет существующие результаты. Изменение порядка ступеней создаёт новую версию и показывает затрагиваемые должности/людей; текущие заявки сохраняют закреплённую версию либо отменяются отдельным решением с причиной.

**Данные и реализация:** расширить существующие сервисы, а не завести второй grade engine. Предлагаемые новые таблицы: `local_ustar_grade_ladders` (стабильная идентичность), `local_ustar_grade_ladder_ver` (неизменяемые опубликованные ступени/порядок), `local_ustar_grade_bindings` (должность, версия, период применения). Редактируемый draft отделить от опубликованной версии. Существующие `grade_rules`, `grade_requests`, `employee_grades` дополнить ссылками на лестницу/версию и ожидаемой ревизией; события использовать из существующего workflow audit. Одна действующая привязка для должности на момент времени; одна актуальная проекция грейда сотрудника; проверки периода под блокировкой, не только в форме.

Миграция переносит JSON-каталог и явные `careergrade_*` настройки, сохраняя ключи ступеней и текущие записи. Legacy привязки, найденные по имени, выводятся в dry-run и подтверждаются как данные; runtime guessing отключается после cutover. Не распространять консультантскую лестницу на все должности. Опубликованные правила нельзя считать пустыми; отсутствие настройки — нейтральный статус сотруднику и конкретное действие ответственному.

**Где:** `grades.php`, `grade_rules.php`, `classes/{career_grades,grade_rules,grade_promotion}.php`, `data/consultant_grades.json` как источник начальной миграции, `templates/career_grades.mustache`, новые grade templates/forms, `profile.php`, `team.php`, career/route consumers, `db/{install.xml,upgrade.php,access.php}`. Новый `classes/grade_ladders.php` — каталог и версии; общий presenter для профиля, команды и страницы грейда.

**Приёмка:** HR создаёт и публикует лестницу без правки файлов; связывает должность; сотрудник видит те же название и статус в профиле/маршруте/грейдах; подаёт одну заявку; руководитель своей области одобряет или возвращает; повтор клика не дублирует результат; смена должности/правил и ручная коррекция имеют объяснимую историю.

### N03. Понятная модель должности и механизм её применения

**Сейчас:** `positions.php` — большой контроллер; на снимке одновременно hero, граф, матрица, грейды и редакторы, часть оформления конфликтует с темой. Пользователь не видит простого порядка настройки.

**Целевой UX:** вход — компактный список должностей с поиском, подразделением, статусом настройки и действием «Открыть». Не выбирать первую должность автоматически. Карточка конкретной должности имеет breadcrumbs и пять разделов:

| Раздел карточки | Что пользователь делает | Что сохраняется |
|---|---|---|
| О должности | Название, подразделение, назначение роли | Существующий ID оргдомена; дата/ревизия |
| Требования | Навыки, обязательный уровень, допустимые источники подтверждения | Черновик/опубликованная версия `standard_model` |
| Обучение и проверка | Привязанный маршрут, материалы, точки и аттестации | Ссылки на существующие версии, scope и политику |
| Грейды | Выбор опубликованной лестницы, переход к её правилам | Та же привязка N02, без второго редактора лестниц |
| Применение и история | Кого затронет, чего не хватает, публикация и прошлые версии | Impact, версия и аудит команды публикации |

Новая должность проходит последовательность «Описание → Требования → Обучение/проверка → Грейды при необходимости → Проверка и публикация». Незавершённый черновик можно сохранить. На существующей должности доступны прямые вкладки; не заставлять каждый раз проходить мастер заново. Необязательная лестница явно обозначается как необязательная.

Механика применения: должность → опубликованный стандарт → требования и привязанные версии обучения → действующее назначение сотрудника → проверяемые факты → квалификация на дату. Публикация показывает список затронутых людей и необходимость новых назначений/переобучения. Не завершать обучение и не начислять награды при публикации стандарта. Общие точки и локальные overrides следуют ADR-0004; отключённый override не возвращает скрытый fallback. Граф навыков остаётся дополнительным представлением, не главным редактором.

Разделить `positions.php` на тонкий controller, presenter и прикладные команды `position_model`/`standard_model`. Одни команды доступны через UI/API/CLI; валидируют отсутствующие источники, пустые обязательные требования, устаревшую ревизию и несовместимые связи. Права на изменение должности и права повышенного доступа не выводятся из её названия.

**Где:** `positions.php`, `classes/{position_model,standard_model,route_model,route_scope,organization_model}.php`, `templates/positions.mustache` с partials, `positions_workspace.js`, `positions_workspace.css`, `theme/ustar/scss/_positions.scss`, `route_studio.php`, `organization_settings.php` для согласованных переходов.

**Приёмка:** человек без знания внутренней схемы проходит создание и применение должности; за ≤3 перехода из HR-пульта открывает её требования или маршрут; неопубликованная/пустая модель не показывает «квалифицирован»; счётчики и ссылки совпадают с командой и профилем; дизайн не меняет исходные брендовые элементы.

### N04. Человеческие названия в уведомлениях регистрации

**Причина подтверждена:** `registration_service::notify_reviewers()` вставляет `$departmentid` прямо в текст `target_core::notify()`.

Исправление — общий formatter/label resolver оргобъектов: ID остаётся ссылкой, в тексте отображается название подразделения, а должность — только если она действительно заявлена или подтверждена. Не называть подразделение должностью. Для исчезнувшего объекта — «Подразделение недоступно» и ссылка на заявку, а не внутренний код.

Новые уведомления хранят ссылку на заявку, ID сущностей и snapshot названия на момент события. Переименование подразделения не переписывает исторический факт; при необходимости карточка показывает и актуальное название. Добавить структурированную metadata/version в существующий inbox, если её нет. `eventtype` отображать русским типом «Регистрация сотрудника», без `local_ustar · registration_requested` в обычной карточке. Action URL ведёт к конкретной заявке с серверной проверкой доступа.

Старые сообщения: связать с существующей заявкой через проверяемые ключи/данные; построить исправленное представление, сохранив исходное событие. Для пакетного backfill — dry-run, точные ID, повторяемость, отчёт неоднозначных связей. Не выполнять глобальную замену похожих строк в сообщениях. Если связь не восстановлена, показать нейтральное описание и карточку регистрации без придуманной должности.

**Где:** `classes/registration_service.php`, `classes/{workflow_notifications,target_core,communication}.php`, `notifications.php`, `templates/notifications.mustache`, RU lang strings, inbox metadata migration. Общий resolver используется также в задачах/грейдах/ленте, с пакетным чтением названий.

**Приёмка:** новая и старая доступная заявка показывают понятное подразделение; после переименования/архива нет `dept_*` в пользовательском тексте; дубль доставки не создаёт второго уведомления; непричастный пользователь не открывает заявку по URL.

### N05. Чек-листы как рабочая вкладка задач

`tasks.php?tab=checklists` сразу показывает доступные чек-листы и выбранную рабочую форму. Убираем промежуточную карточку «Открыть чек-листы», отдельный hero и дублирующую навигацию. Компактный список/фильтр даты + форма; при отсутствии назначений — одно понятное пустое состояние, без двух пустых колонок. Выбор первого доступного чек-листа здесь допустим как явно видимое выделение, без записи данных.

Вынести сборку данных и обработку из `checklists.php`/external в общий `checklist_service` и presenter; оба входа используют их. Старый GET URL перенаправляет в вкладку, сохраняя проверенные `id` и дату. Старый POST на период совместимости обрабатывает та же команда с прежними проверками, затем PRG; нельзя терять ответы редиректом POST → GET. `checklist_studio.php` остаётся инструментом автора по capability, связанным из вкладки для уполномоченных.

Одновременно закрыть D04: версия определения закрепляется в run; редактируемый черновик и окончательная отправка разделены. Опубликованное определение неизменно; изменение создаёт версию. Финальная отправка содержит snapshot версии/ответов/actor/времени; коррекция — новая запись со ссылкой на предыдущую. Ежедневная проекция не перетирает историю отправок. Использовать существующие `check_runs`, `check_answers`, `check_submits`, расширив их; новую таблицу `local_ustar_check_def_ver` вводить для версий определений, а не для второго контура исполнения. Unique/idempotency для пользователя, назначения/даты и отправки; дата по согласованному рабочему timezone.

Самоотметка остаётся самоотметкой. Квалификационный evidence создаётся лишь по явной опубликованной policy, при необходимости после проверки; адаптационные чек-листы сохраняют свои связи и полномочия.

**Где:** `tasks.php`, `checklists.php`, `checklist_studio.php`, `classes/checklists.php`, новые `classes/checklist_service.php` и presenter, `classes/external/{get_checklists,submit_checklist,hr_get_checklists,hr_save_checklists}.php`, `classes/native_data.php`, `templates/checklists.mustache` как рабочий partial, `home.php`, `db/install.xml`, `db/upgrade.php`.

**Приёмка:** вкладка сразу рабочая; черновик переживает перезагрузку; публикация V2 не меняет отправленную V1; двойное нажатие не дублирует факт; старые ссылки работают; чек-лист не присваивает навык самовольно.

### N06. Задачи, личный блокнот и вложения любого формата

Сохраняем четыре понятные вкладки: «Назначено мне», «Мои поручения», «Чек-листы», «Личный блокнот». По прямой ссылке открывается нужная вкладка. По умолчанию — назначенные мне задачи; пустой список не заставляет проходить дополнительную навигацию.

Для задач: компактные карточки/строки с автором, исполнителем, сроком, статусом и следующим действием; фильтры активные/на проверке/завершённые, поиск и пагинация. Форма создания раскрывается по кнопке. Карточка задачи показывает описание, вложения, результат и историю. Действующий процесс сохраняется: назначена → в работе → на проверке, если она требуется → выполнена; возврат и отмена требуют причины. Изменение срока/исполнителя — отдельная проверяемая команда, revision и событие; недоступный получатель не исчезает молча.

Для блокнота: список заметок, поиск только владельца, редактор выбранной заметки, завершение/редактирование/удаление с подтверждением. Не выводить полную форму редактирования под каждой карточкой. Заметки и их вложения не включать в командный поиск, уведомления, HR-аналитику и просмотр от имени сотрудника. Системное обслуживание файлов не означает право руководителя читать блокнот.

**Вложения:** любой формат принимается как файл, без списка только PDF/изображений. Использовать Moodle File API и filemanager с draft area; постоянные filearea `task_attachment` и `task_result`, itemid задачи/события результата. Блокнот использует ту же задачу с owner-only ACL, а не публичный каталог. Настройки размера/количества ограничиваются конфигурацией Moodle, PHP и веб-сервера; эффективные ограничения видны до загрузки. «Любой формат» не означает неограниченный объём.

Сервер проверяет владельца draft, размер, количество, реальное содержимое/тип для preview и право целевого объекта при каждом скачивании. Активные/неизвестные форматы выдаются как download, без исполнения и inline HTML/SVG. Preview только для безопасных обработанных типов; имя экранируется. Загрузка использует штатную антивирусную интеграцию, если она настроена; отсутствие сканера не выдаётся за проверку безопасности. Версия формы защищает от подмены вложений параллельным сохранением. После финализации результат и его файлы привязаны к версии события; отмена draft очищает только бесхозные временные файлы штатным механизмом.

**Производительность:** сейчас `tasks.php` читает все три списка и для HR перебирает всех пользователей до выбора вкладки; `events()` вызывается по каждой отображённой карточке. Перенести загрузку на активную вкладку; получателей выбирать серверным поиском по scope; список 25 элементов с limit максимум 100, события/файлы — пакетно или по открытию карточки. Счётчики вычислять отдельной общей агрегатной выборкой, не загрузкой всех задач.

**Где:** `tasks.php`, `classes/learning_tasks.php`, новые task forms/presenter и шаблоны, `lib.php::local_ustar_pluginfile`, `db/install.xml`/`upgrade.php` для необходимых индексов/связей, `stage6.css` с переносом общих стилей в тему, `classes/privacy/provider.php` в общем privacy-пакете.

**Приёмка:** создать поручение с изображением, PDF, архивом и произвольным бинарным файлом; скачать только в разрешённом scope; отправить результат, вернуть/принять; проверить другой user ID и прямой URL файла; приватная заметка нигде не раскрывается; число запросов не растёт на каждый элемент списка.

### N07. Лента академии

**Вход:** новый пункт «Лента» в левой навигации рядом с «Главная»; `/local/ustar/feed.php`. Лента открывается сразу: редактор публикации, фильтры «Все доступные / Академия / Моё подразделение / Мои публикации», постраничная хронология по `(publishedat, id)` с кнопкой «Показать ещё». Экран подразделения фильтрует тот же feed — отдельную копию постов не создавать.

**Публикация:** текст с безопасным форматированием, изображения/файлы, явный переключатель «От чьего имени», аудитория, предпросмотр, черновик, публикация, редактирование своей доступной публикации и удаление с историей. Опубликованный пост показывает издателя (человек / подразделение / академия), дату и отметку редактирования; реальный actor всегда сохранён в аудите. На телефоне — одна колонка, изображения адаптивные; тяжёлые медиа загружаются лениво. Лайки, комментарии и репосты входят в первую поставку, не остаются заглушками.

| Действие | Сотрудник | Руководитель подразделения | Гендиректор, ассистент гендиректора, HRD, HR |
|---|---|---|---|
| Публикация от себя | Да, активный employee | Да | Да |
| Публикация от подразделения | Нет | Только действующая управляемая область | Только если есть отдельный соответствующий scope |
| Публикация от академии | Нет | Нет по одному факту руководства | Да, через явно выданную capability |
| Настройка аудитории поста академии | Нет | Нет | Да: академия целиком либо выбранные подразделения |
| Лайк, комментарий, репост | Только доступный пост | То же | То же, без неявного обхода ACL |
| Модерация чужого контента | Нет | Только при отдельном разрешении в области | Отдельная capability модератора; публикация от академии её сама не даёт |

Предлагаемые capabilities: `feedpublish`, `feedpublishdepartment`, `feedpublishacademy`, `feedsetaudience`, `feedmoderate`. Выдаются через существующий сервис access profiles и явные Moodle role IDs; имя человека, строка должности и принадлежность к HR-отделу не дают право автоматически. Нужные бизнес-роли из запроса сопоставляются в настройках; если роль ассистента сейчас не выделена, для неё задаётся явный профиль. Pending/terminated/test/service не публикуют в рабочую ленту; тестирование — в изолированном контуре. `view_as` только чтение в пределах целевого доступа.

**Начальная политика видимости:** личный пост — активным сотрудникам академии; пост подразделения — его действующим сотрудникам и уполномоченным участникам управленческой области; публикация академии — выбранной разрешённой аудитории, по умолчанию всем активным сотрудникам. Для департаментской публикации расширение на всю академию выполняется через уполномоченную академическую публикацию, а не произвольным выбором менеджера. Эти значения фиксируются в ADR как предлагаемые продуктовые defaults и могут быть скорректированы владельцем перед реализацией.

Audience ACL применяется в SQL до лимита, при открытии карточки, поиске, уведомлении, скачивании, комментарии и реакции. При переводе/увольнении доступ меняется по действующей занятости. Кэш обязан учитывать пользователя, scope revision и audience revision. Нельзя прочитать закрытый пост по ID, счётчику, картинке или репосту.

**Социальные действия:**

- Лайк — одна запись `(postid, userid)`; повтор запроса идемпотентен, снятие тоже. Счётчик серверный, обновляется атомарно; клиентский optimistic UI откатывается при ошибке.
- Комментарий — безопасный текст, автор/время/ревизия, один уровень ответов для понятного UI; редактирование своего, мягкое удаление с отметкой и сохранением требуемого аудита. Ветки загружаются отдельно, есть пагинация.
- Репост — ссылка на исходный пост, а не копия закрытого тела/файлов. Видимость — пересечение аудитории репоста и оригинала; нельзя расширить доступ. При удалении/закрытии оригинала — «Публикация недоступна» без содержимого. Повторный репост с тем же ключом не дублируется.
- Жалоба/скрытие модератором — основание, actor, журнал и возможность контролируемого восстановления; права модерации независимы от права вести блог.
- Уведомления о комментариях/ответах — существующий inbox/outbox, дедупликация и ограничение частоты; не делать массовую рассылку каждому сотруднику при каждом лайке. Публикация ленты не порождает учебную награду.

**Предлагаемая схема:** `local_ustar_feed_posts` (actoruserid, publishertype, publisherid, status, audienceversion, body/format, version, publishedat, timestamps, sourcepostid), `local_ustar_feed_audience` (postid, scopekind, scopeid), `local_ustar_feed_comments` (postid, parentid, actor, body, version/status), `local_ustar_feed_reactions` (postid, userid, kind; unique), `local_ustar_feed_events` (редактирование, смена видимости, удаление/модерация), `local_ustar_feed_reports` (жалобы и решения). Репост хранится типом post со ссылкой на оригинал. Индексы по status/publishedat/id, publisher, audience scope/postid, postid/commentid; строгие связи и защитные проверки в сервисе. Draft отделён статусом и недоступен аудитории.

Это новые сущности нового продукта, а не дублирование материалов или задач. Имена полей уточняются при XMLDB migration review с сохранением указанного контракта. Вложения — File API `feed_attachment`, itemid стабильного attachment/version объекта; новая редакция не подменяет файлы старого события. Для аудита редакций хранить минимально необходимые данные с retention, не бессрочный дубликат всех удалённых персональных текстов.

**Где:** новые `feed.php`, `classes/{feed_service,feed_access,feed_query}.php`, `classes/output/feed.php`, `classes/form/feed_post_form.php`, `templates/feed*.mustache`, AMD-модуль взаимодействий; существующие `db/{access.php,install.xml,upgrade.php}`, `lib.php`, inbox/outbox, `theme/ustar/layout/ustar.php` и новый theme partial стилей. API, если нужен AJAX, остаётся тонким адаптером к этим сервисам. Добавить privacy metadata/export/deletion для постов/комментариев/реакций/файлов и административный retention.

**Приёмка:** четыре типа авторства проверены на положительных и отрицательных сценариях; смена руководителя отзывает право писать от подразделения; доступ к старым постам определяется явной политикой; лайки/комментарии/репосты работают после reload; закрытый исходник не раскрывается через репост/файл/уведомление; нет N+1, полной загрузки комментариев или пересчёта всей ленты на открытии страницы.

### N08. Форма саморегистрации

Сохраняем текущий брендовый рисунок слева и форму справа, содержимое и порядок смысловых блоков. Не меняем персонажа, не создаём новый макет и не удаляем иллюстрацию. На desktop выравниваем ширины, отступы и вертикальную ось; имя/фамилия могут стоять рядом при достаточной ширине, остальные поля — в устойчивой сетке. На mobile один столбец без обрезки кнопки и горизонтального скролла. Уменьшаем пустоту/излишнюю высоту, сохраняя читабельность и нормальный размер полей.

Короткое объяснение: «Создайте профиль. Подразделение подтвердит HRD». Подразделение — поиск по допустимому справочнику, видимое название и стабильный ID на сервере. Пароль — штатная политика Moodle, показать/скрыть, `autocomplete=new-password`; ошибки у полей и общий фокус на первом ошибочном поле. Значения безопасных полей сохраняются после отказа, пароль не возвращается в HTML/логи. Кнопка соответствует auth-дизайну, ссылка входа явно видна. Повтор submit защищён от дубля аккаунта/заявки.

Бизнес-процесс ADR-0005 сохраняется: manual account + pending + одна HRD-заявка в транзакции, вход в собственный профиль, без обязательного письма подтверждения. Не возвращать устаревшее email signup из раннего аудита. До решения нет обучения, команды, ленты и файлов через прямые входы. Сохраняем sesskey, throttle и anti-bot проверки.

**Где:** `register.php`, `templates/register.mustache`, `classes/registration_service.php`, `theme/ustar/layout/login.php` если требуется раскладка, `theme/ustar/scss/_login.scss`, общий form partial/RU lang. Точные размеры проверяются на присланном макете, не угадываются по thumbnail.

**Приёмка:** исходная композиция узнаваема и выровнена; регистрация, неверный пароль, занятый login/email, пустой/невалидный department и повтор отправки имеют понятный результат; одна заявка; ожидающий сотрудник видит статус и не получает рабочие права.

## 4. Производительность и согласованность всей академии

Работа начинается с короткого baseline на согласованном стенде, а не с тяжёлого нагрузочного прогона. Замерять время сервера, число SQL, память, объём HTML/JS/CSS и время основного действия для home, team, positions, grades, tasks/checklists, notifications и feed. Отдельно cold/warm cache и обычный/управленческий пользователь. Данные и конфигурацию замера фиксировать; без стенда эти метрики остаются «не измерено».

| Проблема/область | Изменение | Проверяемый результат |
|---|---|---|
| Загрузка всех вкладок tasks и всех получателей | Запрос только активной вкладки, server-side autocomplete, batch events | Объём работы ограничен размером страницы |
| Grading/evidence по одной записи в цикле | Пакетный fetch опубликованных правил/версий/evidence, один resolver | Запросы не растут линейно с карточками |
| Большой positions controller и DOM графа | Presenter, lazy вторичные вкладки, граф по запросу | Список должностей не строит все графы/редакторы |
| Метрики с пределом 500 и последующей фильтрацией | Scope/filter до pagination; агрегаты по полному разрешённому набору | Люди за первой страницей учтены; total/hasMore честные |
| Общее меню/роль в теме | Готовая scoped navigation viewmodel; кэш с инвалидированием назначений/ролей | Тема не делает повторный кадровый обход на каждом блоке |
| Непредсказуемые writes при чтении маршрута/грейда | Явные команды, очереди проекций и read models | GET/preview не меняет обучение/экономику; свежесть показана |
| Синхронные доставки и массовые пересчёты | Пакеты cron с cursor, retry/backoff, dedup, failed state | Быстрое действие пользователя, видимый lag и безопасный повтор |
| Новая лента/файлы | Keyset pagination, индексированный audience, thumbnails и lazy media | Нет полной ленты/комментариев в первом ответе |
| Дубли CSS/JS и тяжёлые assets | Один stylesheet компонента, AMD только нужной странице, сборка assets | Нет повторной загрузки legacy board/editor и каскадных конфликтов |

Начальные бюджеты: p95 server response типового списка/карточки ≤1 секунды на согласованном объёме; ключевые действия ≤3 переходов; страницы списков по 25 строк, серверный максимум 100; увеличение числа видимых строк не добавляет запрос на каждую строку. Точный SQL/memory budget фиксируется после baseline. Для UI ориентиры — LCP ≤2.5 с и отсутствие заметного сдвига формы/карточек на согласованном устройстве/сети; это цели, не заявление о текущем production.

Тяжёлые полные отчёты — асинхронный экспорт с областью, временем среза, прогрессом и проверкой доступа при скачивании. Кэш не служит новым источником истины; инвалидируется после commit по версии объекта/области. Для ключевых SQL — EXPLAIN на репрезентативных обезличенных данных; новые индексы добавляются под реальные условия, не на каждое поле.

## 5. Оставшиеся инженерные изменения

Эти работы обязательны для закрытия всего аудита. Сначала исправляются зависимости новых функций, остальное — после восьми пунктов и общего UI/performance прохода.

### R-ORG: права, кадровые данные и адаптация

1. Устранить подтверждённое расхождение: `adaptation_service::is_hrd_actor()` ожидает роль `hrd` от `structure::resolve_user()`, который возвращает employee/head/superadmin. Использовать явное полномочие операции и scope, не строку роли/должности; согласовать с `capabilities`, ADR-0005 и кадровыми решениями.
2. Устранить случай HR-сохранения без должности: `hr_people` ожидает конфликт `no_active_primary_assignment`, а resolver для человека без истории возвращает пустой список конфликтов. Допустить согласованный статус «без должности», не создавать фиктивное назначение. Изменение контактных данных не должно требовать кадрового назначения.
3. Все writers профиля/импорта/штатного места/назначения используют один кадровый command contract; интервалы PRIMARY/ACTING, capacity, future hire/termination, renew window и ручные reporting overrides проверяются одинаково.
4. Запланированное кадровое решение отделить от факта вступления в силу; защиту от преждевременного исполнения сохранить. Фоновое применение имеет idempotency и видимую ошибку. Timezone и фактический рабочий календарь не выводятся из часового пояса случайного текущего оператора.
5. Адаптация: все transitions, смена владельца/руководителя, два конкурирующих решения, отмена и повтор — единая state machine. Заявитель регистрации не становится автоматически руководителем адаптации.
6. Убрать остаточные name-based оргэвристики после явного переноса блоков/ролей; не расширять полномочия сотрудникам HR-отдела. Нормализацию оргсправочников по ADR-0002 довести через один writer и адаптер чтения, с отчётом конфликтов JSON/assignments.

Основные файлы: `classes/{adaptation_service,hr_people,organization_identity,organization_model,staffing_requests,team_access,company_hierarchy,capabilities,position_access,structure}.php`, tasks кадровых проекций, `db/access.php`, migration/preflight CLI.

### R-LEARN: маршруты, evidence, аттестации и экономика

1. `route_model::create_version()` использует другой lock factory/key, чем save/publish. Объединить writer boundary. Учитывать, что `attach_published_content()` уже держит route lock: публичная команда + внутренние locked primitives устраняют риск повторного захвата и deadlock. Пустые обязательные требования/provider проверяются во всех входах, включая миграционные адаптеры.
2. Убрать enrol/completion/assessment sync из обычного `route_model::for_user()` и reconciliation из чтения грейда. Перенести в команды результата/начала/кадрового изменения и повторяемый background repair. GET видит сохранённое состояние и объяснимый pending sync, а не выполняет бизнес-операцию.
3. Общий completion/evidence reader для route, profile, grade, team и analytics: та же версия, свежесть, cutoff и `as of`; исторические corrections учитываются только с момента события. Не возвращать старую квалификацию по новой версии автоматически.
4. `target_core::decide_gate()` должен проверять полноту опубликованной gate policy, требуемые skills/evidence, сроки, actor и expected state под общей блокировкой. Одной принадлежности evidence пользователю недостаточно. До готовности не показывать gate как действующий допуск.
5. Сохранить completion cycles, идемпотентные награды каждого нового подтверждённого прохождения, cutoff старой истории, исключение test/service из экономики и reversal вместо удаления ledger. Повтор одной версии при новом цикле — новый факт, refresh страницы — нет.
6. Forced retraining оформить явным назначением с target manifest, причиной, сроком, cutoff и состоянием; существующие workflow events остаются историей. Новая индексируемая проекция/таблица восстанавливается из событий только там, где связь однозначна; конфликт не замалчивается.
7. `catalog_mastery`: заменить константы POINT_ID/SCORM_CMID/next и разбор HTML на опубликованную конфигурацию привязки и нормализованный контракт источника. Сохранить действующий production mapping через dry-run.
8. Завершить версионность игровых вопросов/попыток и опросников; версия evidence/политики и reward basis фиксируется в результате. Одновременный pass/remediation/финальная оценка не создаёт два перехода.

Основные файлы: `classes/{route_model,route_scope,assessment_policy,assessment_lifecycle,target_core,route_rewards,forced_retraining,catalog_mastery,analytics,standard_model}.php` и фактические сервисы completion/evidence; `route_studio.php`, внешние API, cron, install/upgrade. Перед правкой проверить точные имена потребителей через code map; перечисление доменов не разрешает создавать дубли отсутствующего сервиса.

### R-CONTENT: материалы, доставка и продуктовые входы

Сохранить уже реализованное ознакомление с точной версией; довести единый revision/lock для edit/move/archive/publish. Pinned/latest-compatible — явная связь с показом влияния обновления. Page/search/file применяют один ACL. Старые версии остаются доступны в разрешённой истории факта.

Уведомления: объединить `workflow_notifications` и `target_core::notify` вокруг одного inbox/outbox; сделать delivery worker с attempt/nextattempt/error/delivered, retry/backoff, dead-letter и операторским повтором. Отправка наружу не держит доменную транзакцию. Для Bitrix сначала установить, используется ли он и есть ли внешний worker: при включении нужен рабочий adapter, при отключении — явное состояние disabled, а не вечное pending. Аналогично почта. Общий unread в меню и центре, без двойного счёта локальных и Moodle сообщений.

Сверить task/goal/gate/board feature → entrypoint. Старые Boards уже сняты и архивированы: не восстанавливать редактор ради старого пункта D08; сохранить owner-only архив и отказ старым write API. «Состояние» не возвращать отдельной пустой страницей. HR-пульт довести до пяти разделов из аудита: Обзор, Моя команда, Должности и обучение, Материалы, Отчёты; переключатель «Управление / Моё обучение» не меняет права и не лишает HR личного маршрута.

### R-OPS: приватность, поставка и эксплуатация

- Добавить `classes/privacy/provider.php`: metadata, export/delete policy для существующих и новых персональных данных и файлов; разграничить удаление личного контента и необходимые неизменяемые факты/законные retention-исключения. Сроки хранения и RTO/RPO утверждаются владельцем, не выдумываются разработчиком.
- Инвентаризация опасных CLI; dry-run, явный actor/target manifest, ограничения production и журнал. Разделить DDL upgrade и большой backfill; fresh install/upgrade должны давать одинаковую schema.
- Manifest точного SHA: версии Moodle/PHP/PostgreSQL/plugins, assets hashes, migration prerequisites, зависимости и SBOM. Сборка из фиксированных lockfiles; не развивать второй frontend параллельно, но сохранить его контракт/сборку до подтверждённого вывода из эксплуатации.
- Proxy: reserved fields, endpoint allowlist, токены/expiry/rotation, отсутствие секретов в URL/логах, разрешённые реальные hostnames. Патчи frontend зависимостей учитывают реально установленную сборку.
- Мониторинг cron age, queue lag, failed delivery, repair backlog, projection conflicts; request/correlation ID без паролей, токенов и приватных заметок. Задача не считается выполненной по одной созданной строке очереди.
- Restore репетировать для согласованного набора БД + moodledata + source + config; откат schema не сводится к `git checkout`. Нужны эксплуатационные preflight/rollback и обновлённый контекст точного SHA.

## 7. Миграции и совместимость

Все новые схемы — XMLDB `install.xml` + монотонный `upgrade.php` + версия плагина. Точные номера версий выбираются по актуальному HEAD непосредственно при реализации. Схема новых installs и upgrade должна совпасть. Новые поля сначала допускают безопасное переходное состояние; ужесточение constraints — после сверки.

Порядок: inventory/dry-run → backup manifest → additive schema → пакетный backfill → отчёт соответствий и конфликтов → переключение единственного writer → совместимые reader-адаптеры → проверка → отключение legacy writers. Не оставлять неопределённый dual-write. Сначала переходить доменами: grade, checklists, files/feed, затем оставшиеся орг/learning проекции. Проект нового feed пустой, поэтому его migration не затрагивает исторические учебные факты.

Для каждого преобразования описать: прежний источник, новый владелец, ключ сопоставления, допустимые null/unknown, порядок locks, idempotency, batch size/cursor, expected duration, проверку количества/ссылок, rollback. Непривязанный старый грейд/чек-лист не пропадает: он попадает в отчёт и разрешённую историю.

Совместимость URL: workspace → команда/структура; checklists → tasks tab с сохранением объекта; grade_rules → каноническая настройка; позиции сохраняют стабильные object URL; старые API сохраняют прежний контракт на период перевода потребителей или явно версионируются. Инвентаризация legacy consumers обязательна перед удалением файла. Нельзя удалять таблицу только из-за отсутствия совпадений в одном grep.

## 8. Проверки без тяжёлого прогона на каждую функцию

Владелец требует три базовые проверки и один общий тяжёлый Moodle DB этап после подготовки всех функций. Новую CI-схему для каждой функции не строим. Используем существующий `.github/workflows/ustar-review-gate.yml`.

**Важная особенность текущего кода:** source/frontend выполняются на обычном PR; rollback и Moodle DB сейчас включаются одним `full_rc`/label `full-rc`. Сам rollback — полноценная Docker-репетиция восстановления, а не lint. Чтобы выполнить именно три проверки перед общим DB suite, в G10 минимально разделить ручной запуск: например `rollback_only=true` включает существующий rollback без Moodle DB. Исходный полный gate сохранить. Не подменять успешный restore статической проверкой shell и не запускать full-rc на каждый пакет.

| Момент | Что выполняется | Что это доказывает |
|---|---|---|
| Локально после осмысленного пакета | PHP/JS/AMD syntax/build затронутого, XMLDB/template/source checks, короткий ручной сценарий при наличии стенда | Нет явного синтаксического/контрактного сбоя; не DB/production acceptance |
| Обычный code PR / объединённые изменения | Существующие source и frontend; использовать результаты того же SHA, не повторять без причины | Базовая проверка исходников, существующих fixtures и frontend build/security |
| Все изменения собраны, перед тяжёлым Moodle | Три базовых gate: source + frontend + существующий rollback отдельным запуском | Собранный код и восстановление изолированной системы проверены |
| Финальный frozen RC | prepare-rc + общий Moodle DB: fresh install, upgrade, repeat upgrade, доменные сценарии всего пакета | Совместимость полной схемы и поведения на реальном Moodle/БД |
| Перед/после деплоя владельцем | Browser smoke, read-only integrity и runtime manifest, проверка очередей/cron | Конкретная установленная сборка и ключевые рабочие сценарии |

Тяжёлые регрессионные сценарии готовить рядом с изменениями только для существенного риска (ACL, конкуренция, migrations, данные/награды), запускать вместе в G11. Не писать отдельный тест на каждую перестановку CSS. Если общий тест выявил дефект — исправить и повторить затронутые проверки; существенная правка схемы/доменных контрактов требует подтверждения окончательного SHA, а не ссылки на старый PASS. Время экономится объединением, не игнорированием ошибок.

Минимальный общий набор: регистрация → pending → HRD → назначение/доступ; HR без должности; роли HRD/HR/manager/employee/assistant и отрицательный scope; создание должности/лестницы/правил/грейда; чек-лист V1/V2 и correction; задача/результат/вложения/приватный блокнот; feed author/audience/comment/repost/file ACL; route publish concurrency; cycle/reward/retry/reversal; content exact ack; evidence/gate/as-of; >500 сотрудников и paginate; preview не пишет; restore и старые URL.

Для этого планового docs-PR продуктовые проверки и тяжёлый DB вручную не запускаются. Проверяется полнота документа, ссылки, 8 новых пунктов, 60 audit ID, 13 старых дефектов и отсутствие изменений продукта.

## 9. Декомпозиция для Goal-режима

Одна цель: **подготовить следующий RC на базе актуального production-кода, закрывающий восемь требований и исходный аудит, с доказуемыми данными/правами, единым интерфейсом и инструкцией владельцу для выпуска**. Каждая строка — самостоятельный проверяемый шаг, а не разрешение пропустить зависимость. Работа запускается только после отдельной команды владельца.

Один интеграционный RC может содержать последовательные reviewable commits; отдельный тяжёлый pipeline на каждую фичу не нужен.

## 10. Что будет передано для деплоя

Кодовый PR/ветка и tag/commit с точным SHA, source archive и assets, manifest с checksum, release notes по-русски, миграционный dry-run/отчёт, таблица приёмки 8+60+13, результаты трёх gate и общего Moodle DB, инструкция владельцу с командами preflight → backup → maintenance → установка → Moodle upgrade → assets/cache → cron → smoke → выход из maintenance, плюс чёткие условия остановки/отката.

Команды будут привязаны к проверенным mount paths и версиям из актуального manifest. Исторические пути `/opt/ustar/...` и контейнеры из переписки не считать неизменными. Не выдавать готовую команду распаковки нового релиза до появления самого артефакта и проверки совместимости. При migration rollback восстанавливается согласованный комплект БД/moodledata/code/config; новые файлы/посты и персональные данные учитываются политикой backup/retention.

Для окончательной проверки понадобятся от владельца или согласованного стенда: read-only manifest после выпуска 26.09, роли/access profiles без секретов, репрезентативные обезличенные объёмы, доступный путь визуальной приёмки, действующие ограничения upload, политика хранения и RTO/RPO. До этого кодовая работа может идти, но runtime-пункты не получают выдуманный PASS. Доказательства по удержанному владельцем сбросу истории №4 записываются отдельно.

**Критерий готовности:** все 8 новых требований реализованы; все 60 audit ID и 13 прежних дефектов имеют проверяемое решение без молчаливого исключения; основные роли проходят сквозные сценарии; нет известных блокирующих дефектов/расхождений данных/прав; достигнуты согласованные UX/performance критерии; общий DB gate и комплект восстановления подтверждены. Неподтверждённый пункт остаётся открытым и мешает заявлению «аудит закрыт». После деплоя владельцем выполняется отдельная production-приёмка.
