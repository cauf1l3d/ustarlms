# USTAR Academy — инфраструктурная продакшен-стратегия

**Назначение:** обеспечить стабильность, устойчивость, безопасность и — главное — **монетизируемость** продуктовой стратегии
**Основание:** инфраструктурный аудит (06.10) + сверка реального кода репозитория `cauf1l3d/ustarlms`
**Модель:** on-premise поставка в контур заказчика + внутренняя эксплуатация в компании
**Дата:** октябрь 2025

---

## 0. Главный принцип этого документа

Инфраструктура здесь рассматривается **не как техническая гигиена, а как коммерческий актив**.

Формулировка, которую нужно принять как аксиому:

> **Каждый незакрытый инфраструктурный риск — это либо заблокированная сделка, либо неоплаченный счёт, либо репутационный удар, который убивает следующие сделки.**

Это не метафора. Прямая механика:

| Инфраструктурный пробел | Как именно он блокирует деньги |
|---|---|
| Роль PostgreSQL со superuser | Security-ревью заказчика закрывается на стр. 1 вопроса. Сделки нет |
| Нет TLS | ИБ-служба заказчика не согласует. Сделки нет |
| Нет Privacy API | Вопрос об экспорте/удалении данных субъекта ПДн → отказ |
| Нет проверенного restore | Нельзя подписать SLA с RTO — а без RTO нет корпоративного контракта |
| Нет мониторинга/алертинга | Вы не знаете о сбое; клиент узнаёт первым. Второго года не будет |
| Нет иммутабельного кода | Дрейф конфигурации неотличим от дрейфа на площадке клиента. Вы не можете воспроизвести проблему |
| Нет проверенного апгрейда | Клиент боится ставить ваши обновления. Он остаётся на старой версии и уходит |

**Ключевое следствие:** приоритет инфраструктурных работ определяется **не технической критичностью, а тем, что именно блокирует продажу**. Это отличает эту стратегию от обычного инфраструктурного плана.

⚠️ **Важный порядок, отличный от аудита.** Аудит ставит работу с разделами диска (GPT/рост раздела) на первое место, поскольку таково распоряжение владельца. С точки зрения риска порядок должен быть другим: **сначала обратимое и срочное, потом необратимое.** Изменение разметки диска на сервере, где живут почта, DNS и ISPConfig, — единственная операция, после которой может не быть «после». Поэтому в этой стратегии она перенесена в конец фаз и выполняется **только после** проверенного восстановления сегмента.

### 1.2. Целевая архитектура (не переусложняя)

**Принцип:** один сервер, никаких Kubernetes, никакого service mesh. Всё, что ниже — минимально достаточный уровень для 100–200 пользователей и для продажи в контур заказчика.

```
                        ┌──────────────────────────────────┐
   Клиент (браузер) ────│  Apache / TLS-терминация         │
                        │  отдельный vhost, НЕ default      │
                        └──────────────┬───────────────────┘
                                       │ 127.0.0.1:8082
                        ┌──────────────▼───────────────────┐
                        │  ustar_moodle (web + cron)        │
                        │  код: read-only                   │
                        │  запись: только moodledata        │
                        └──────────────┬───────────────────┘
                                       │ internal network
                        ┌──────────────▼───────────────────┐
                        │  ustar_postgres                   │
                        │  роль ustar_app (без superuser)   │
                        └──────────────┬───────────────────┘
                                       │
              ┌────────────────────────┼────────────────────────┐
              │                        │                        │
     ┌────────▼────────┐    ┌──────────▼─────────┐   ┌──────────▼────────┐
     │ Prometheus      │    │ pgBackRest / wal-g │   │ HDD: архивы        │
     │ + exporters     │    │ WAL + base backup  │   │ (офсайт-копия)     │
     │ + Alertmanager  │    │                    │   │                    │
     │   → Telegram    │    │                    │   │                    │
     └─────────────────┘    └────────────────────┘   └────────────────────┘
```

**Разделение ответственности (критично для on-premise).** В контуре заказчика часть слоёв принадлежит ему. Это и есть та матрица, которую ждут в тендере.

| Контроль | В вашем контуре | В контуре заказчика |
|---|---|---|
| Приложение и его обновления | **Вы** | Применяет клиент по вашей процедуре |
| БД, схема, миграции | **Вы** | Эксплуатация — клиент |
| TLS, сертификаты | Вы (шаблон) | **Клиент** (его УЦ / его домен) |
| Идентификация (IdP, SSO) | Вы (интеграция) | **Клиент** (его провайдер) |
| Резервное копирование | Вы (автоматизация) | **Клиент** (его носители, его политика) |
| Мониторинг инфраструктуры | Вы (поставляемые дашборды) | **Клиент** |
| Периметр, сеть, файрвол | — | **Клиент** |
| Физическая безопасность | — | **Клиент** |
| Обработка запросов субъектов ПДн | **Вы** (инструмент в продукте) | **Клиент** (как оператор ПДн) |

Эта таблица — прямой ответ на вопрос тендеров «что именно покрыто вашим соответствием, а что эксплуатацией заказчика». Без неё заказчик считает, что вы обещаете больше, чем можете.

## 2. Безопасность: закрытие подтверждённых рисков

### 2.1. P0-1. Роль приложения в PostgreSQL имеет cluster superuser

**Факт (аудит, 04.10 23:57 UTC):** роль `moodle` — SUPERUSER + CREATEROLE + CREATEDB + REPLICATION + BYPASSRLS.
**Усугубляющий фактор:** `www-data` может писать в `config.php` и `local/ustar`.

**Почему это критично, а не «в теории».** Связка «веб-приложение может писать в свой конфиг» + «роль БД — superuser» означает: компрометация веб-слоя = полный контроль над СУБД, включая базы других клиентов на этом общем сервере. Для on-premise-продукта это ещё и вопрос доверия: заказчик увидит ту же конфигурацию у себя.

**Что делать:**

| Шаг | Действие | Критерий приёмки |
|---|---|---|
| 1 | Ввести роль `ustar_app` — OWNER схемы, права DML + последовательности, **без** admin-флагов | upgrade/web/cron работают на ней |
| 2 | Ввести роль `ustar_migrator` — только для `admin/cli/upgrade.php` | Миграции проходят под ней |
| 3 | `postgres` — только для ручных аварийных операций | Задокументирован доступ |
| 4 | Прогнать на копии: web, cron, install, upgrade, backup, **restore** | Всё зелёное **до** снятия флагов |
| 5 | Снять флаги в проде | Проверено повторно |
| 6 | Убрать единственный неверифицированный admin без дублёра | Второй администратор существует |

**Стоп-правило:** не снимать флаги вслепую и не оставлять единственного непроверенного администратора.

### 2.2. P0-2. TLS

**Факт:** Академия доступна по HTTP через vhost `ustar.local`. HTTP vhost — не TLS-прокси.
**Что это значит:** пароли сотрудников, cookie сессии и WS-токен идут открытым текстом. `cookiesecure=1` в БД **не** защищает, пока сессия стартует по HTTP.

**Что делать:**
- отдельный TLS-vhost, **не затрагивая** default/ISPConfig и другие сайты;
- внутренний УЦ или сертификат на внутреннее доменное имя;
- редирект HTTP → HTTPS;
- `Secure` / `HttpOnly` / `SameSite` на cookie;
- повторная проверка: login/logout, файлы, чат, SCORM/H5P, задания.

**Для продукта:** клиенту поставляется **шаблон** конфигурации TLS, но сертификаты — его (он владеет доменом и УЦ). Это фиксируется в матрице ответственности (раздел 1.2).

### 2.3. P0-3. Privacy API

**Факт:** в `local_ustar` отсутствует `classes/privacy/provider.php`.

**Почему это блокирует B2B.** Любой корпоративный заказчик с персональными данными сотрудников спросит: как реализован экспорт и удаление данных по запросу субъекта ПДн. Это не «хорошо бы», это элемент соответствия 152-ФЗ.

**Что делать — по документированному паттерну Moodle:**

| Метод | Что реализует |
|---|---|
| `get_metadata` | Описание персональных данных в таблицах плагина и передач во внешние системы |
| `get_contexts_for_userid` | Поиск контекстов с данными конкретного пользователя |
| `export_user_data` | Экспорт данных в **разрешённых** контекстах, с человекочитаемым смыслом, не сырыми ключами |
| `delete_data_for_user` | Удаление данных одного пользователя **без** ущерба записям других |
| `delete_data_for_all_users_in_context` | Обработка вывода контекста из эксплуатации |
| `get_users_in_context` / `delete_data_for_users` | Массовые операции по группе в контексте |

**Критерий приёмки (end-to-end):** взять бывшего сотрудника и показать: какие данные о нём есть в Moodle и связанных системах; почему каждая позиция хранится; что содержит экспорт; что удалено; и что удаление не повредило записи других сотрудников.

**Что API **не** делает (важно не обещать лишнего).** Privacy API — инструмент, а не соответствие. Правовые основания обработки, сроки хранения по целям, уведомление и роли — решения организации, их нельзя «включить». Отдельно: **согласие сотрудника не является надёжным правовым основанием для обязательного обучения** из-за дисбаланса власти работодатель–работник — это прямо отмечено в руководстве EDPB. Правовое основание должно определяться **по каждой цели** отдельно.

### 2.4. P1. Иммутабельность кода и прав

**Факт:** `www-data` пишет в `config.php` и `local/ustar`. «Legacy» — резервный механизм задач.
**Проблема:** при on-premise вы обязаны уметь воспроизвести состояние у клиента. Если код может меняться на площадке — вы не можете.

**Что делать:**
- код в проде — **read-only**; запись только в `moodledata`;
- изменения конфигурации — через ops-скрипт, не вручную;
- инвентаризация владельцев, ACL, write-прав по родительским каталогам;
- проверка, что закрытие записи **не ломает** обновление, создание кэша и доставку релиза;
- старые дампы: `0644` и проходимые родительские каталоги — закрыть; архивы **вне** каталогов приложения.

### 2.5. P1. Секреты

| Что | Состояние | Что делать |
|---|---|---|
| `.gitignore` | Настроен корректно: `.env`, `*.key`, дампы вне git — проверено | Оставить |
| Старые дампы | `0644`, проходимые родители | Закрытые каталоги, внешнее хранилище |
| Ключи | Отдельная копия есть, расшифровка проверена | Регламент ротации после проверки реального раскрытия |
| Rule | Не публиковать config/env/dumps/logs «для доказательства» | Достаточно обезличенных статусов |

## 3. Устойчивость: доступность, восстановление, деградация

### 3.1. P0. Проверенное восстановление

**Факт:** ручной trial HDD прошёл 06.10 (PASS, 957 МБ, readback, login HTTP 200). Но: `last_scheduled_run=null`, восстановление **именно из этого архива** не проверено, внешняя доставка ручная, RPO/RTO нигде не зафиксированы числами.

**Почему это блокирует монетизацию.** Корпоративный контракт с SLA невозможен без зафиксированных RPO/RTO. А зафиксировать их можно только после того, как восстановление доказано **измерением**.

**Что делать:**

| Шаг | Действие | Критерий |
|---|---|---|
| 1 | Restore-drill HDD-архива на **отдельной машине** | Логин, курсы, оценки, файлы — PASS |
| 2 | Замерить время восстановления | **Зафиксировать в минутах** — это ваш RTO |
| 3 | Установить целевые RPO/RTO числами | Например, RPO ≤ 1 ч; RTO ≤ 4 ч — подставить измеренное, не выдуманное |
| 4 | Включить WAL-архивирование (`pgBackRest` / `wal-g`) | RPO падает с «суток» до «минут» |
| 5 | Доп. pg_dump каждые 6 ч | Страховка от логического повреждения |
| 6 | Внешняя копия — автоматически + checksum + алерт при неудаче | Нет «ручной доставки по выводу владельца» |
| 7 | Повторить drill, уложиться в RTO | Доказанная воспроизводимость |

**Про шифрование архивов.** Архивы шифруются (`.age`) — это правильно. Ключ хранится отдельно и расшифровка проверена — тоже правильно. **Сохранить эту практику для продукта:** on-premise-клиент захочет шифрованные архивы на своих носителях.

### 3.2. P0. Мониторинг и алертинг

**Факт:** общей установленной системы нет, проверенной доставки нет. Сейчас о падении cron, заполнении диска или деградации СУБД вы узнаёте от пользователя.

**Минимально достаточный стек (один сервер, без переусложнения):**

```
node_exporter        → метрики хоста
postgres_exporter    → метрики СУБД
blackbox_exporter    → HTTP-проверка логина (внешняя точка зрения на доступность)
        ↓
Prometheus           → сбор и правила алертинга
        ↓
Grafana              → один пульт
Alertmanager         → маршрутизация
        ↓
Telegram             → доставка
```

**Обязательные алерты (не «хорошо бы», а минимум):**

| Алерт | Условие | Почему именно так |
|---|---|---|
| Cron freshness | нет успеха > 10 мин вне согласованного окна | Аудит: exit 0 **не** заменяет результат задачи |
| Enabled task overdue | с учётом effective-enabled, overrides, timezone | 17 задач COMPONENT_DISABLED учитывать отдельно |
| Adhoc queue | возраст / размер / failed + динамика | Не только total |
| Backup | нет успешного бэкапа > 26 ч; пауза бэкапа с причиной и временем начала | Backup-lock не должен бесконечно глушить алерт |
| Storage | место, **inode**, абсолютный остаток, рост; SMART | Пороги 80%/90% — согласовать, не «на глаз» |
| PostgreSQL | connections > 80% от `max_connections`; блокировки; долгие транзакции | Без этого деградация невидима |
| HTTP | доля 5xx > 1%; латентность > порога | blackbox ловит «сайт лежит» раньше пользователя |
| Auth | всплеск неудачных входов | Ранний признак подбора паролей |

**Правило по метрикам:** не собирать personal labels, не давать полный доступ к docker socket, не давать cluster superuser для мониторинга, не давать произвольный shell. Мониторинг — самая атакуемая поверхность.

**Для продукта:** поставляемая конфигурация дашбордов и правил алертинга — это **часть продукта**, а не ваша внутренняя настройка. Клиентский ИТ-отдел должен получить рабочий пакет. Это существенно повышает сделку: вы приходите не с приложением, а с эксплуатационной системой.

### 3.3. P1. Производительность и ёмкость

**Факт:** `max_connections=100`, `shared_buffers=128 MiB`, `work_mem=4 MiB` — дефолты. Оптимальность **не измерена**. Нагрузочный тест не проводился. Крупнейшая известная нагрузка — пилот ~8 человек; история — 18 человек.

| Шаг | Действие | Критерий |
|---|---|---|
| 1 | Включить `pg_stat_statements` | Видны top-20 запросов по времени |
| 2 | Снять **baseline до** тюнинга | Зафиксирован p95 по ключевым сценариям |
| 3 | Нагрузочный тест (k6 / Locust): логин + чтение дашборда + список задач | **Зафиксирована цифра**, а не мнение «хватит на 200» |
| 4 | Тюнинг: `shared_buffers` ~25% RAM, `work_mem` 8–16 MiB, `effective_cache_size` | Повторный замер p95 |
| 5 | `autovacuum` для горячих таблиц (feed, notifications, tasks) | Нет роста мёртвых строк |
| 6 | Индексы под реальные выборки | По result из `pg_stat_statements`, не по интуиции |

**Требуемая нагрузка для чёткости:** целевой профиль — 100–200 одновременных активных пользователей в пике. Замерять и на 200, и на 400 (запас ×2) — чтобы знать, где ломается, а не где «должно работать».

### 3.4. P1. Неограниченные выборки в коде

**Факт:** `hr_get_people.php` — 250 записей за проход; `materials.php` — цикл по строкам; `global_search.php` — поиск по всей базе.

**Сейчас** база 104 МБ — незаметно. **Через год** историй — станет узким местом, причём **у клиента**, где вы не можете быстро вмешаться.

**Правило (не рефакторинг, а дисциплина):** один новый список в коде = один явный `LIMIT` + пагинация. Проверять на code review.

### 3.5. Устойчивость к деградации (для продукта)

То, что заказчик спросит и что не должно стать сюрпризом на внедрении:

| Сценарий | Требуемое поведение |
|---|---|
| БД недоступна | Приложение не «сыпет» ошибками в интерфейс; понятное сообщение, логирование, восстановление |
| Внешний IdP недоступен | Локальный fallback для админа, либо понятная деградация |
| Диск заполнен | Алерт сранее; приложение не портит данные |
| Cron не работал сутки | Признак в пульте; накопившиеся задачи обрабатываются корректно |
| Апгрейд сломался | **Откат < 1 ч** — процедура описана и проверена на стенде |

## 4. Эксплуатация: то, что делает продукт сопровождаемым

### 4.1. Установщик (главный рычаг юнит-экономики)

**Проблема:** развёртывание сейчас = ручные действия владельца (`USTAR_CRON_SETUP`, `USTAR_HDD_SCHEDULE`, правки `config.php`, Apache vhost, контейнеры). **Это убивает масштабируемость: каждое внедрение — ваш выезд.**

**Требование:** идемпотентный bootstrap одной командой.

```
зависимости → проверка требований → БД и роли → Moodle core →
плагин + тема → конфигурация → сервисы → healthcheck → отчёт
```

**Критерий приёмки:** развёртывание «с нуля» **< 1 дня**, воспроизводимо, с отчётом о каждом шаге.

### 4.2. Импортёры миграции

**Проблема:** клиент приходит с историей из iSpring / Excel / SAP / старого Moodle. Без импорта **сделки не закрываются** — внедрение встаёт на первой неделе.

**Минимум для старта:** Excel/CSV (структура, люди, история обучения) + SCORM-пакеты. Далее — целевые коннекторы по спросу.

### 4.3. Процедура обновления на стороне клиента

Клиентский ИТ-отдел должен получить регламент:

- как ставится патч;
- как проверяется успех (healthcheck);
- **как откатывается** — и за какое время;
- что происходит с данными при откате;
- как обновляется ядро Moodle и что с правками ядра.

### 4.4. Документ «Требования к инфраструктуре»

Обязательный элемент поставки: ОС, CPU/RAM/диск, версия PostgreSQL, PHP, порты, исходящие соединения, что нужно открыть в файрволе, минимальные требования для пилота и для продакшена на 200 и на 500 пользователей.

### 4.5. Управление версиями у N клиентов

**Проблема:** через год у каждого клиента своя версия. Вы утонете в матрице.

**Политика:**
- поддерживаются **текущая и предыдущая минорная** версия;
- контрактное требование обновляться;
- автоматический апгрейд-путь, покрытый CI (у вас уже есть тест **повторного** upgrade — это ваш козырь, показывайте его в тендере);
- метрика «число версий в поддержке» ≤ 2.

### 4.6. Ноль правок ядра Moodle

**Факт (аудит core comparison):** 24 678 совпадающих файлов, **1 изменённый**, 23 лишних, missing/errors = 0. Полная эквивалентность upstream — **false**.

**Проблема:** каждый изменённый файл ядра — это патч, который надо переприменять при **каждом** обновлении Moodle, на **каждом** клиенте.

**Что делать:** журнал правок ядра; цель — ноль; неизбежную правку выносить в upstream или оформлять как формализованный патч с тестом и записью в release-ledger.

## 5. Разведение контуров: prod и lab

**Факт:** четыре контейнера, активные bind-mounts, lab «нельзя считать свободным от использования каталогом». Рядом живут почта, DNS, ISPConfig.

**Риск:** lab-конфиг подменит prod-конфиг или порт. Это не гипотеза, это самый частый способ уронить продакшен «на ровном месте».

**Минимальные меры (без переезда):**
- раздельные compose-проекты и префиксы имён: `ustar-prod-*` / `ustar-lab-*`;
- lab — в собственной сети;
- **запрет монтировать production-каталоги в lab**;
- `--pull never` с иммьютабельными image ID для lab (у вас это уже есть в cold checkpoint — расширить на все lab-процессы);
- отдельные ресурсные и лог-лимиты.

**Стратегическая мера:** отдельная VM/машина для Академии. Пока Академия делит коробку с почтой и DNS, **любое ваше действие — это риск для компании**, а не только для продукта.

## 6. Операция с разделами диска: почему она последняя

Инфраструктурный аудит ставит работу с GPT и рост корневого раздела первым пунктом по распоряжению владельца. Технически возражение одно и оно весомое:

**На этом сервере живут: Moodle, PostgreSQL, почта, DNS, ISPConfig, четыре контейнера и активный lab. Операция с GPT — единственное действие, способное необратимо убить всё сразу.**

**Предлагаемый порядок:**

| # | Условие «до» | Зачем |
|---|---|---|
| 1 | Проверенный restore (раздел 3.1) | Если что-то пойдёт не так — есть из чего восстанавливаться |
| 2 | Уведомление и участие владельца | Это операция владельца инфраструктуры, не «админа» |
| 3 | Окно обслуживания + консольный доступ | Reboot может потребовать консоли |
| 4 | Полный backup метаданных и данных | — |
| 5 | Независимая post-check: CRC, pointers, GUID, entry array, boot preservation | Посторонний чек, а не скрипт, который делал операцию |

**Отдельно:** перед любым широким изменением проверяется **реальное** восстановление с учётом его области (scope), а не «подготовленный» скрипт. Backup timer сам по себе не допускает пропуск stage/rollback.

## 7. Продуктовый смысл инфраструктуры: что из неё продаётся

Это раздел, который отвечает на вопрос «как инфраструктура монетизируется».

| Инфраструктурный артефакт | Как продаётся |
|---|---|
| **Матрица ответственности вендор/клиент** | Прямой ответ на вопрос тендера «что покрыто вашим соответствием» |
| **Архитектурная диаграмма с доверительными границами** | Обязательный элемент RFI/RFP |
| **Пентест-отчёт** | Требуется в тендерах явно, включая API по OWASP |
| **Требования к инфраструктуре** | Первое, что спросит ИТ-отдел; отсутствие = задержка внедрения на недели |
| **Процедура патчинга + откат** | Снимает главный страх ИТ-директора |
| **Дашборды и алерты как часть поставки** | Вы приходите с эксплуатационной системой, а не с приложением |
| **Зафиксированные RPO/RTO** | Основа SLA и корпоративного контракта |
| **CI с тестом повторного upgrade** | Доказательство зрелости процесса; редкость на рынке |
| **Privacy API** | Открывает корпоративные сделки |
| **Шифрованные архивы с внешним ключом** | Соответствие требованию ПДн; уже реализовано |
| **Ноль правок ядра** | Предсказуемость обновлений — ваш аргумент против кастомных решений |

**Ключевая мысль:** вы можете прийти к заказчику **без единой новой функции**, но с этим пакетом — и это будет убедительнее, чем конкурирующий LMS с красивым интерфейсом. Потому что заказчик покупает не красоту, а снимаемый риск.

## 10. Риски и что делать

| # | Риск | Вероятность | Мера |
|---|---|---|---|
| 1 | Работа с GPT на общем сервере убьёт почту/DNS | **Средняя, но необратимая** | Перенести в конец; проверенный restore до |
| 2 | Lab подменит prod-конфиг | Средняя | Раздельные проекты, запрет монтажа prod в lab |
| 3 | Дрейф конфигурации у клиента | **Высокая** | Иммутабельный код, ops-скрипт, инвентаризация прав |
| 4 | Апгрейд сломает прод клиента | Средняя | Процедура + откат, проверенный на стенде |
| 5 | Матрица версий у N клиентов | **Высокая** | Политика ≤ 2 версий, контрактное требование |
| 6 | Мониторинг обнаруживает слишком много «шума» | Высокая | Пороги согласовать с владельцем, а не «на глаз» |
| 7 | Правки ядра накопятся | Средняя | Журнал + цель ноль |
| 8 | Нехватка ресурса на инфраструктуру и продукт одновременно | **Высокая** | Порядок фаз; инфраструктура в фазах 0–2 как условие продаваемости, а не «когда-нибудь» |

## 11. Итог: три вещи, определяющие всё

1. **Инфраструктура — не техдолг, а условие продажи.** Каждый P0-пункт блокирует конкретную сделку, а не «качество». Пока они открыты, продуктовая стратегия нереализуема, сколько бы функций ни было написано.
2. **Порядок важнее полноты.** Сначала обратимое (БД, мониторинг, restore, TLS), потом необратимое (разделы диска). Аудит прав насчёт перечня, но не насчёт последовательности — и эта поправка спасает компанию от худшего сценария.
3. **Эксплуатационный пакет — часть продукта.** Дашборды, процедуры, матрица ответственности, требования к инфраструктуре — это то, что превращает приложение в поставляемую систему и **что скопировать у вас конкуренту сложнее, чем функции**.

> **Главная мысль:** деньги в этой модели приносит не код, а способность развернуть, сопроводить, доказать безопасность и предсказуемо обновить. Инфраструктурная стратегия — это и есть монетизационная стратегия, просто записанная техническим языком.
