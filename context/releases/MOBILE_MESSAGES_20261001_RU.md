# USTAR: исходный логин, рабочие чаты и мобильная оболочка

Кандидат расширяет exact PR71 hotfix c77ba822. Установщик
`scripts/release/deploy_mobile_messages.sh FULL_SHA` принимает только побайтно
совпадающие PR71 4cbb8ac3 (3006/3004) или c77ba822 (1001/1001), делает backup и
ставит оба компонента 2026100102. Роли и таблицы не меняются. Деплой выполняет
владелец; production этой разработкой не изменён.

## Что проверять после установки

1. Выйти и открыть логин на desktop/телефоне: прежняя графика и персонаж,
   штатные вход/ошибка/восстановление/внутренняя регистрация, одинаковые колонки.
2. После входа: главная/блокнот/каталог без add_body_class error; «Настроить
   главную» стоит после всех персональных блоков, настройка работает.
3. Сообщения: диалог, текст, изображение/видео/аудио/документ, просмотр и скачивание,
   прогресс загрузки, ошибка размера без потери текста, последнее сообщение в длинной
   истории, предыдущая страница, сохранение черновика при потере сети.
4. Создать рабочую группу, переименовать, добавить и убрать коллегу. Новый участник
   видит историю; исключённый теряет чат и прямую ссылку на вложение. Чужой участник
   не меняет состав; Moodle course group не управляется как рабочая группа.
5. На 320/390/768px проверить разные роли: навигация «Ещё» содержит все доступные
   разделы; формы, таблицы, обучение/Quiz/SCORM, каталог, задачи, заметки, HR и
   студии. При клавиатуре поле отправки и кнопка остаются доступны. Локальная
   прокрутка большой доски/таблицы допустима; прокрутка всей страницы по X — дефект.
6. По защищённому адресу добавить на домашний экран Android/iOS, запустить и
   войти в отдельном окне. При отключённой сети показывается объяснение, без
   сохранённых приватных страниц. После смены учётки старое содержимое не кэшируется.

## HTTPS во внутренней сети

`http://ustar.local` не является secure context на телефоне. Manifest не меняет
это ограничение браузера. Для install promotion требуется HTTPS с доверенным
сертификатом; localhost в CI — отдельное исключение для разработки.
Источник: https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable

Вариант для текущего внутреннего имени: блок из
`scripts/release/mobile/Caddyfile.internal.example` с `tls internal`. Это добавление
одного host к текущему Caddyfile, без публикации Академии наружу. В host-based
Caddy upstream — наблюдённый loopback `127.0.0.1:8082`; для Caddy в Docker нужно
использовать фактический адрес Apache в его Docker network.

До изменения нужны только факты: местоположение Caddyfile, запуск Caddy
(host/container), существующие host/upstream и DNS на телефоне. Проверка на сервере:

```bash
sudo docker ps --format '{{.Names}} {{.Ports}}'
sudo systemctl status caddy --no-pager
getent hosts ustar.local
```

После объединения блока с существующим конфигом: `caddy validate --config
<actual Caddyfile>` и штатный reload существующего сервиса. Root CA Caddy
передать в корпоративное хранилище доверенных сертификатов и доверить на
клиентах; браузер не должен показывать ошибку сертификата. Не обходить её
`--ignore-certificate-errors` и не заявлять install acceptance с `curl -k`.
Источник: https://caddyserver.com/docs/automatic-https

Затем change wwwroot в существующем config.php на `https://ustar.local`; если
TLS завершается на proxy перед HTTP Apache, включить `$CFG->sslproxy = true`
согласно реальной схеме. Не включать reverseproxy без проверки: запрещённый
обход proxy/Host может сделать текущий доступ неработоспособным. Конфиг с
секретами не отправлять в GitHub. После смены схемы выполнить штатный cache
purge и проверить login/POST/медиа/Quiz/SCORM/worker по новому адресу.
Старые абсолютные ссылки в содержимом проверить отдельно; автоматическая
глобальная DB replace в этот UI-релиз не включена.

Установщик сообщает HTTP origin как незавершённое условие установки приложения.
Код адаптации можно установить независимо от сетевого cutover; полноценную
production-приёмку PWA завершать только после DNS/HTTPS/client trust.

## Откат

После upgrade не понижать только version.php. Восстановить согласованный backup
БД, кода и moodledata при maintenance; пользовательские сообщения/файлы, созданные
после backup, требуют отдельного решения о сохранении. Новый CDN/внешний сервис
или отдельная messaging database не нужны.
