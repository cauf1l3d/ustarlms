# Пользователи и персональные уведомления пульта

Продолжение запроса владельца18Oct18:55МСК из shared chat6ad4f002. Последняя реплика агента19:06 описывает работу, но GitHub head83635d60 её не содержит. Не считать установленные1c881495 новыми исходниками этой доработки.

Цель: владелец создаёт/меняет/отключает локальных viewer/operator/owner в браузере; пользователь связывает свой личный Telegram по одноразовому коду и настраивает свои уведомления. Последний активный owner защищён, изменение роли/пароля/блокировка отзывает сессии. Текущая парольная/TOTP-if-enrolled reauth и CSRF обязательны для изменений доступа. Старые пользователи и bootstrap Telegram IDs сохраняются.

Auth SQLite остаётся доступен только web UID. Telegram token/outbox и новый store привязок/настроек остаются только notifier UID. Web общается с notifier через локальный Unix socket с SO_PEERCRED только web UID; notifier не получает auth hashes. Бот принимает /link CODE только из личного не пересланного сообщения, user_id=chat_id, не bot; TTL10мин, хеш кода в DB, одноразовость, один Telegram ID на одну учётку. Корневые bootstrap IDs остаются доступными; настройки уведомлений к их ID можно привязать доказательством владения. Динамические привязки отозванных учёток отключаются до изменения пользователя; отказ RPC не должен оставлять ошибочно подтверждённый отзыв.

Настройки: enabled, check_ids (фиксированный каталог), statuses warning/critical/no_data, repeat_minutes15..1440, quiet_start/quiet_end HH:MM либо пустые, timezone из IANA, recovery bool. Дополнительные персональные CPU/RAM пороги cpu_percent1..100/ram_available_percent1..99 и hold_seconds0..3600. Настройки и состояния независимы по получателю; отключение/отвязка отменяет pending alerts для него; команды /status остаются доступными. Порог CPU/RAM считает только свежие валидные измерения и сбрасывает hold при пропусках. Тихие часы задерживают до актуальной оценки, без последующей отправки очереди устаревших событий.

API контракт: GET /api/admin/users => {users:[{username,role,enabled,totp,sessions}]}; POST /api/admin/users {username,role,new_password,password,otp}; PATCH /api/admin/users/{username} {role?,enabled?,new_password?,password,otp}. GET /api/account/telegram => {linked,telegram_id?,preferences,catalog,transport_status}; POST /api/account/telegram/link {password,otp} => {code,expires_at,instruction}; POST /api/account/telegram/unlink {password,otp}; PUT /api/account/notifications {preferences,password,otp}. Все account routes относятся только к текущему username; admin может создать системному администратору учётку, тот входит и связывает собственный Telegram.

Наблюдаемость: доступность events независима от status журнала запросов во всём collector→snapshot→UI. source_empty не считается отключённым журналом; для пустого успешного events показывается отсутствие предупреждений. Реальные запросы не подменяются синтетическими; безопасная диагностика показывает настройки/числовые счётчики без raw logs.

Полное отсутствие питания/сети нельзя определить и сообщить с того же хоста. Подготовить схему исходящего heartbeat в независимый managed сервис без собственного второго сервера; не активировать внешнюю отправку/создавать аккаунты без данных владельца. Не обещать различение power/LAN/ISP по одному missing heartbeat. При работающем хосте локальные службы/контейнеры/HTTP и доставка Telegram остаются разными признаками.

Без native SSH; не менять DNS/firewall/routes/VPN/CA/TOTP. Поставка: regression backend+browser, role/CSRF/last-owner/migration/link/replay/quiet-hours tests, independent review, GitHub exact-source CI и проверенный архив, команды update без повторного setup.

## Проверка и ограничение отзыва

Связывание/настройки сериализованы с изменением пользователей через Auth transaction: ранее начатая сессия не создаёт код после отзыва. Отзыв notifier завершается до изменения доступа; при занятом/недоступном worker операция отклоняется, её можно повторить после обновления состояния. Отдельные root-configured bootstrap Telegram IDs сохраняют свой исходный доступ независимо от web-привязки; отключение динамической учётки не редактирует секретный allowlist. CLI reset остаётся локальным способом восстановления администратора.

Независимое ревью исправило четыре сценария доставки: повторные события после сброса настроек имеют уникальный durable key; интервал повторов отсчитывается от фактической доставки; отмена до доставки при обслуживании не маскирует текущую аварию; отсутствующая проверка в fallback снимке отменяет устаревшее событие. Проверенные переходы не заменяют native Telegram ACK конкретного получателя.
