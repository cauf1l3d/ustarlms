# Управляемая группа Telegram: проект следующего выпуска

Статус: проект подготовлен для review; код и сервер не изменены.
Исходная задача владельца: после принятого пилота продолжить подготовку управляемого подключения других сотрудников с личным согласием и текущими правами.

## Исходная точка и цель

[Квитанция пилота](../runtime/connect_notification_pilot_owner_20261021.json): один сотрудник Moodle UID 130, реальное сообщение о задаче, переход в Академию и задачи, обычный вход без сессии, полный отзыв связи и отсутствие сообщения по новой задаче. Эти проверки повторно не открываются. Последний read-only SQL показал revoked 1 / linked 0 при включённых предпочтениях; повторная привязка владельцем не подтверждена.

На сервере worker/tool a86e208029b6104150e85d0e90384f84da214c22 с исправленным доступом к каталогу. В репозитории staging исправлен на 172610616d91539a6725d27c1ac62fa83f4e963b; его CI Context 39595204430 / Review 39595203810 SUCCESS, включая 7 actual-UID33 pilot tests. Менеджер и журнал принятого a86 привязаны к его точному source_commit. Подмена их пакетом нового commit без процедуры перехода недопустима.

Результат следующего выпуска: оператор задаёт от 1 до 10 конкретных Moodle ID; связанные с ними действующие сотрудники лично управляют подпиской. Сообщения уходят только разрешённым участникам и только по новым событиям. Отзыв связи или согласия прекращает будущую доставку, права в Академии остаются каноническими. Первая группа и перечень её ID выбираются владельцем при установке готового пакета, а не агентом сейчас.

Это изменение архитектуры поставки существующего контура: новые группы не требуют новых бизнес-таблиц, ролей, endpoint или нового бота. До реализации требуется review этого проекта, затем отдельный план реализации. Работа выполняется в существующем feature checkout PR #106; субагенты запрещены владельцем.

## Рассмотренные варианты

| Вариант | Преимущества | Цена и граница |
|---|---|---|
| Один отправщик с явной группой 1–10 | Существующий worker уже поддерживает до 10 subjects, PHP fence — до 10 UID; сохраняется одна очередь | Изменения группы требуют проверяемого согласования обоих списков |
| Отдельные отправщики для участников | Раздельное состояние процессов и credentials | Потребуются partitioning существующих leases, дополнительные unit/ключи и правила координации |
| Открытая подписка всем связанным сотрудникам | Минимум ручного управления членством после общего запуска | Более широкий выпуск, другие operational и browser-trust gates; независимый ограниченный список worker перестаёт ограничивать первую группу |

Выбран первый вариант для первого расширения. Размер 10 следует из существующих ограничений `notification_worker.py` и `notification_delivery.php`, а не является заявкой на подключение всей организации. Более широкий rollout рассматривается отдельно по результатам группы.

## Поведение для сотрудника

1. Сотрудник входит в Академию своей учётной записью и лично выполняет существующую двухстороннюю Telegram-привязку. Добавление ID оператором не создаёт связь, учётку или права.
2. Сотрудник включает «Получать уведомления в Telegram» и нужные категории. Сохраняются его важность, тихие часы, часовой пояс и интервал. Оператор их не изменяет.
3. Участник выбранной группы получает новые допустимые события. Текст и кнопка остаются существующими: подробности и действия доступны в native Академии с обычной сессией/входом.
4. Отзыв связи/согласия или удаление из группы блокирует будущие отправки. Сообщение, отправка которого уже началась до изменения, не отзывается из Telegram. Новые проверки используют события, созданные после изменения.
5. Смена Telegram-аккаунта требует обновления оператором разрешённого соответствия UID→subject. Новая связь сама по себе не наследует разрешение прежнего Telegram subject. Пароли Академии в Telegram не вводятся.

Нет нового интерфейса пульта, MiniApp, provider-login, HR/руководительских действий или автоматического согласия. Работа с остальными сотрудниками и очередями не изменяется.

## Списки участников и отсечка

CLI принимает повторяемый `--userid`, например `--configure --userid 130 --userid 131`. Разрешены 1–10 различных положительных Moodle ID; дубли, пустой набор и превышение 10 отклоняются до остановки служб. Режима `all` и неявного добавления сотрудников нет.

Read-only проверка выбирает для каждого UID действующий business account, текущее employment ACTIVE и ровно одну активную private Telegram-связь нужного tenant. Telegram subjects берутся из канонических записей, пользователь не вводит их вручную. Subjects различны. Для UID 130, пока связь revoked, configure с130 откажет до записи; оператор либо ждёт личного повторного связывания, либо выбирает других уже связанных сотрудников.

В PHP остаётся непустой строгий `ustar_connect_notify_userids`, в private sender config — соответствующий `notification_subjects`. Оба списка согласуются в одной управляемой операции; malformed/missing runtime config не разрешает отправку. Глобальный sending flag никогда не включается при отсутствующем UID fence. Canonical проверки employee/link revision/preferences/scope перед lease/begin сохраняются.

Каждое применение нового состава задаёт новую общую отсечку событий для всей группы. Старые события не досылаются при добавлении/повторном добавлении участников. Это сознательная граница первого расширения: ожидающие события до новой отсечки не превращаются в новую Telegram-рассылку. Записи Академии, её задачи и существующие receipts не удаляются; uncertain отправки не повторяются автоматически. Журнал фиксирует состав, отсечку и номер поколения до первой записи конфигурации. Восстановление незавершённой операции использует это же поколение; новая отсечка появляется только при следующем явном configure.

## Переход с a86 и журнал восстановления

Рекомендуется отдельный root controller и журнал `/var/lib/ustar-connect-notify-rollout` с правами 0700. Старый `/var/lib/ustar-connect-notify-pilot` и его исходные before-images сохраняются; source-bound проверки не ослабляются до принятия произвольного commit.

Первый configure принимает только известный активный a86 pilot journal и проверяемые deployed bytes/metadata, immutable release, accepted PHP policy, managed units, scope/private TLS и единственный receiver. Baseline verification не требует, чтобы старый получатель130 оставался связанным: его добровольный revoke сохраняется. Все выбранные для новой группы UID проверяются отдельно.

До первого изменения создаются durable снимки фактической конфигурации, указателя релиза, переданных link/include images/state, unit/drop-in metadata и enabled/active состояния sender/receiver. Исходный a86 baseline сохраняется отдельно от транзакции последнего изменения группы. Все пути, права, владельцы, hashes и before/after значения проверяются; неизвестные изменения администратора останавливают запись.

Операция выполняется под существующими shared locks. Ввод ID завершается до locks. Новый immutable code release проверяется и получает права 0755, public code 0644, private config/credentials 0600; исправление umask 077 обязательно. Бот-token, ограниченный notification-only ключ, CA и их scopes сохраняются. PHP policy/version 2000/schema и Academy HTTPS/config не переустанавливаются.

После read-only identity/scope/egress preflight останавливается sender, затем единственный receiver для общего code-pointer handoff. Публикуются согласованные UID/subject списки и отсечка, выполняется private no-poll probe, запускаются receiver и sender. SQLite cursor/dedup сохраняется. Никаких тестовых `sendMessage`/`getUpdates` из installer; реальную delivery-приёмку выполняют сотрудники своим действием.

Ошибка до/после частичного handoff возвращает предыдущую проверенную конфигурацию и сохранённые enabled/desired-active состояния служб. Восстановление файлов не требует нового согласия, активной связи прежнего получателя 130 или сетевого ACK. Штатные identity/scope проверки при запуске не обходятся: если сеть недоступна и прежнюю службу запустить не удалось, controller явно сообщает recovery_required и оставляет возможность повторить guarded recovery, не заявляя active. Состояние бизнес-БД, предпочтения сотрудников и SQLite cursor не откатываются. Потеря процесса оставляет журнал для guarded recovery; неизвестный drift не перезаписывается.

После перехода используется новый controller. Legacy a86 CLI обязан безопасно отказаться при новом pointer/config, не начав изменения. Явный rollback возвращает сохранённый a86 baseline и его прежнее состояние отправщика; SQL revoke/личные предпочтения не меняет.

## Команды и остановка

| Команда | Результат |
|---|---|
| Без аргументов | PLAN_ONLY; нет host access/network |
| `--check --userid …` | Read-only проверка выбранной группы и совместимости; без остановки, записей и provider sends |
| `--configure --userid …` | Первая управляемая поставка или новое поколение состава; свежая отсечка |
| `--status` | Проверенное состояние controller, Moodle ID, поколение/отсечка, состояние служб; без токенов, subjects и личных сообщений |
| `--disable` | Sending flag=false, sender остановлен/выключен; receiver и личные связи сохранены; прежний пилот автоматически не включается |
| `--rollback` | Явное возвращение к сохранённому a86 baseline; вывод показывает восстановление прежнего режима sender, что отличается от disable |

При повторном configure автоматическое восстановление возвращает предыдущую группу, а не исходный пилот. Транзакция последнего изменения и исходный baseline имеют разные снимки. При выключенном sender configure может возобновить работу только с явно переданным и проверенным составом и новой отсечкой.

## Изменяемые файлы и границы

- `connect-worker/ustar_connect/receiver_runtime.py`: строгая конфигурация 1–10 subjects, уникальность и прежний запрет linking/onboarding в sender.
- `scripts/infra/connect_notification_rollout.py`: новый root controller; существующие atomic/metadata/locks/guard primitives используются без ослабления старого a86 loader.
- `scripts/infra/build_connect_notification_rollout.py`: exact-source deterministic PYZ, pinned legacy reference, archive/manifest hashes; default plan без доступа к host.
- `tests/r16/test_connect_notifications.py`: допустимые и отказные многопользовательские config cases, независимая sender граница.
- `tests/r16/test_connect_notification_rollout.py`: переход с a86, поколения, disable/rollback, crash и реальные file/UID проверки.
- `.github/workflows/ustar-review-gate.yml`: отдельная strict runtime проверка и frozen artifact. Existing PHP/native/browser regression сохраняется.
- Runtime runbook/receipt и текущие STATE/ACTIVE/BACKLOG/SESSION_LOG/index обновляются при выпуске. Для документации не выдаётся новая production source-версия.

`notification_worker.py` и native PHP fence уже принимают до 10 элементов. Изменять их права/lease API или PHP schema ради расширения не требуется. В реализации любые обнаруженные несовместимости сначала воспроизводятся тестом и отражаются в плане; неизвестный baseline не принимается по предположению.

## Проверки выпуска

Решение владельца 21.10.2026: ручную live-проверку группы сотрудников перенести на этап полного запуска. Сейчас не запрашивать новые назначения, привязки и отзывы ради этой проверки. Она остаётся deferred, а не passed; уже принятый пилот одного сотрудника не переоткрывается. Автоматические, локальные и CI проверки реализации сохраняются. Это решение меняет срок live-приёмки, а не означает выполненную реализацию или установку группы.

1. До кода — RED на конфигурации двух subjects; после — GREEN для 1, 2, 10, отказ для 0, 11, дублей, malformed IDs и linking/onboarding sender flags.
2. Два обычных сотрудника: только свой new event; opted-out/revoked/неактивный/не включённый в группу не получает событие; один revoke не мешает второму. Обновление UID/subject и отсечки не выпускает старую историю.
3. Реальные root metadata и доступ сервисного UID при umask 077. Token/key/CA/cursor и legacy journal сохранены; нет рекурсивных chmod/chown и неизвестных unit overrides.
4. Частичная запись/потеря процесса на каждом handoff, повторный configure, сеть до stop, неизвестный admin drift, disable и rollback при уже revoked UID 130; восстановление прежней группы и source guards.
5. Неподдельный private TLS/systemd credentials fixture, canonical Moodle/PG отрицательные scope/revoke проверки, native browser regressions и полный r16. Modeled systemd не выдаётся за реальный service-user access.
6. Exact Git artifact/hash и инструкция owner. Live acceptance первой группы: два сотрудника лично связывают и разрешают Tasks; уполномоченный actor создаёт новые задачи; собственная доставка/native доступ; revoke одного и продолжение работы второго. Другие категории, общая browser CA trust и весь CON02 этим тестом не закрываются.

## Открытые границы

Реальные Moodle ID первой группы потребуются при подготовке owner configure, не для разработки. Browser/phone доверие существующему CA остаётся задачей организации. Domain/DHCP/маршруты, входящие порты, VPN/proxy и токены не меняются. Bitrix portal/API решения, MiniApp/external HTTPS, native SSO/MFA/role actions и ACK человека не входят в этот выпуск. Telegram API acceptance не считается прочтением сообщения или выполнением задачи.
