23.10.2026, Europe/Moscow. Статус: конкретный проект следующего среза, готов к review;
новый код маршрутизации ещё не написан. Поручение владельца: «ок идем дальше тогда».
Продолжение [CON-02 scope](USTAR_CONNECT_CON02_SCOPE_20261021.md), не новый inbox.
[Фактический server1 checkpoint](../runtime/connect_con02_server1_owner_20261023.json):
application/worker53476482, local2200/theme0202, ACK включён; два личных ACK сохранены.

## Цель и границы

Сотрудник выбирает один основной внешний канал и, по отдельному согласию, один
резервный. Inbox Академии остаётся полной канонической историей. Выбор применяется
к новым событиям; тихие часы, часовой пояс, категории, срочность и интервал
сохраняются. Факт отправки провайдеру, чтение, ACK и выполнение задачи остаются
четырьмя разными фактами. Руководитель не включает чужую личную подписку.

В этом срезе разрабатываются каноническое решение о канале, настройки и проверка
двух синтетических провайдеров. Реальная доступность Bitrix появляется только после
CON-02C и отдельной native portal acceptance. Не показывать сотруднику неработающий
Bitrix как доступный выбор. WhatsApp, digest, автоматические повторы человеку после
uncertain, массовый rollout и изменение бизнес-политики напоминаний сюда не входят.

## Подходы

Единственный подход, соответствующий уже принятому RFC: маршрутизация внутри
Академии поверх существующих notifications/delivery. Создание параллельной очереди
в worker или рассылка во все привязанные каналы противоречат одной истории и
согласованному отсутствию fan-out. Между событиями и попытками хранится явное
решение о маршруте, чтобы конкурирующие workers не выбрали разные каналы.

Поэтому отдельный выбор новой архитектуры не требуется. Конкретное ограничение
этого проекта: резерв используется только ДО первого разрешения внешней отправки.
Это консервативное решение автора проекта, которое предлагается принять вместе
с документом. После begin даже failed/retry_wait не переключаются на другой канал
в B.1; расширение потребует отдельного доказанного контракта «точно не отправлено».

## Настройки и совместимость

Новый строго версионированный JSON в существующем user_preferences, отдельное имя
от `local_ustar_connect_notify_v1`. Поля нынешних настроек сохраняются; добавляются
`primary_channel` и `fallback_channel`. Значения: `none`, `telegram`, `bitrix`;
резерв не может совпадать с основным. Отключение внешних уведомлений оставляет inbox.
Новые настройки сохраняет только текущий реальный пользователь с session/sesskey,
без view-as; ошибочный JSON не включает внешнюю отправку.

Не переписывать все v1 настройки миграцией. Пока v2 не сохранён пользователем,
валидный нынешний v1 opt-in означает тот же Telegram без резерва и с прежними
категориями/quiet/TZ/интервалом. Не создавать новое согласие из существования link.
При явно сохранённом v2 его отказ или выключение имеют приоритет над старым v1;
испорченный v2 запрещает внешнюю отправку вместо восстановления старого согласия.
Включение самого routing feature — отдельная версия профиля, по умолчанию OFF.
Откат профиля сохраняет запись v2; v1 worker не запускается поверх несовместимого
состояния и не должен возобновить внешнюю рассылку вопреки текущему v2 выключению.

## Решение о канале и состояние доставки

1. Существующий canonical writer создаёт один notice и idempotent route в своей
   transaction. route содержит notification ID, выбранный канал, состояние и revision;
   отдельная уникальность по notification ID запрещает второй маршрут. Использовать
   минимальное additive XMLDB расширение, не менять смысл исторических колонок.
2. Для нового маршрута проверяются feature/activation cutoff, recipient fence,
   действительные предпочтения, текущий actor/business scope и активный link с revision
   в соответствующем tenant. Выбирается primary; если он заведомо недоступен ДО begin,
   допускается явно разрешённый, доступный fallback. Если ни один не разрешён — inbox.
3. Перед begin повторяются права, связь, согласие, cutoff, TTL, актуальность события,
   route revision и выбранный канал под тем же каноническим lock. Quiet hours и общий
   recipient cooldown применяются до отправки и после возможного выбора резерва.
4. Отзыв/смена связи и настроек до begin отменяет устаревший permit. Единственное
   разрешённое переключение — с ещё не начатого primary на текущий разрешённый fallback
   той же route transaction. Ранее выданный lease не сможет отправить после переключения.
5. После первого begin маршрут закрыт для автоматической смены канала. Timeout,
   uncertain, provider_accepted и потерянный finish не становятся причиной fallback.
   Known rate-limit повторяется в том же канале с нынешним durable retry budget;
   uncertain сохраняется для явного разрешения, не ставится снова pending.
6. Все delivery attempts ссылаются на один route/notice. ACK не меняет provider receipt,
   не завершает задачу и не снимает отдельные future reminders той же задачи.

Исторические delivery/connectversion1 и ACK v2 продолжают свой принятый lifecycle;
не создавать для них новые route/fallback и не пересылать старую историю. Исторический
`disabled` Bitrix не активируется миграцией. Новые pending можно безопасно отменить
при отключении профиля только до begin; уже начатые состояния остаются durable.
Live SQLite cursor, HMAC scopes и один receiver на провайдера сохраняются.

## UI и недочёты живой проверки

Нативный раздел «Мессенджеры» показывает реальные доступные каналы, основной,
резервный либо «Без резерва», нынешние фильтры/quiet/TZ/интервал и краткое объяснение:
«Подтверждение означает получение уведомления; задача выполняется в Академии».
Недоступный будущий провайдер не маскируется фиктивной успешной настройкой.

Из owner ACK verification: кнопка исчезает после успешного callback, а текст
подтверждения кратковременный. В presentation-срезе сохранить видимую отметку
«✓ Принято · время» в сообщении; повторная обработка сохраняет первое ackat.
Различать ограниченные типы «Назначена задача» и «Напоминание о задаче».
Произвольные заголовки/тексты, action URLs и персональные metadata из Moodle
по-прежнему не выходят в worker. Новое поле presentation допускается только через
явный versioned bridge контракт; не расширять строгий permit v1/v2 на месте.
Точная версия wire и номера новой схемы определяются в implementation plan.

По двум owner SQL строкам нельзя доказать ошибку раннего напоминания: dueat и
policy задачи не получены. B.1 не меняет расписание/эскалации на этом основании.

## Проверка и поставка

- Native PostgreSQL: fresh/2200→new/repeat/paired restore, old100 неизменны вне явной
  миграции; исходные два отсутствующих legacy UNIQUE не исправляются. Гонка двух
  провайдеров/route revision, revoke/settings vs begin и потерянный ответ не дают fan-out.
- Контрактные тесты двух synthetic providers: primary, pre-begin fallback, none,
  no consent/link/tenant mismatch, stale lease и TTL, quiet hours/DST, общий cooldown,
  max attempts/429 и запрет fallback после begin/uncertain/provider_accepted.
- V1 exact preferences retained, valid mapping, explicit v2 disabled/invalid fail closed,
  guarded profile disable/recovery без replay и без возвращения отозванного consent.
- Нативный UI на мобильных ширинах, CSRF/view-as/чужие настройки, доступность формы;
  presentation ACK повтор/потеря Telegram edit сохраняют canonical receipt.
- Runtime regression сохраняет actual UID33/LoadCredential/private TLS и актуальный
  HTTPS topology с отдельным AutoReport9443. Проверять source и owner acceptance отдельно.

Разработка и проверки — самостоятельно, без субагентов. Сначала source/fixtures и
точная CI-квитанция, затем отдельная проверяемая поставка обычным.py. Нынешний4394
остаётся immutable tool для534 payload; не подменять его ссылку на текущий HEAD.
Изменения routing profile/нового wire не устанавливаются на server1 этой документацией.
Групповая живая проверка остаётся отложенной до полного запуска; прежний pilot
и два успешных ACK не требуется повторять ради нового checkpoint.

## Что уже принято и что предлагается сейчас

Из прежнего RFC/scope: одна история, primary/fallback без fan-out, текущие permissions,
согласие и quiet/TZ; сохранение v1; synthetic providers до фактического Bitrix; digest
как отдельная политика. Из owner live evidence: личный Telegram ACK сохранён.

Предлагаемые конкретные решения B.1: отдельное v2 preference без массовой перезаписи,
durable route на notice, fallback только до begin, fail-closed отключение/повреждение
v2, versioned presentation для видимого ACK/различения событий. Approval этого
документа ещё не получен. Следом — конкретный implementation plan на эти границы;
не начинать Bitrix credential configuration или менять production profile.
