# ADR-0007 — Версии грейдовой лестницы и личный грейд

Дата: 27.09.2026. Статус: принято для чернового G05; runtime-приёмка открыта.

## Контекст

Каталог консультантов в JSON и `careergrade_<positionid>` в config смешивали
ступень должности с личным грейдом. Правила перехода уже сохраняют версию
подтверждаемой точки, но не версию самой лестницы. Чтение могло создавать
заявку и показывать первую ступень без персональной записи.

## Решение

`local_ustar_grade_ladders` хранит стабильную идентичность и редактируемый
черновик. `local_ustar_grade_ladder_ver` хранит неизменяемые опубликованные
ступени с hash. `local_ustar_grade_bindings` задаёт единственную текущую
версию для стабильного ID должности и ревизию. Снятие связи сохраняет
строку с пустой версией: старый name-based fallback не оживает. Старые
версии, личные записи и правила не удаляются.

Новые `grade_rules`, `grade_requests` и `employee_grades` закрепляют
`ladderversionid`. Личный грейд появляется только через HR-команду с
основанием либо через подтверждённую заявку сотрудника и решение текущего
руководителя. HR-коррекция и перенос — отдельные команды с причиной,
ожидаемой ревизией и событием аудита. При смене версии личный грейд
не повышается, заявка не одобряется автоматически: нужна явная сверка HR.
Опубликованная версия не меняется при редактировании черновика. Новые
правила перехода закрепляют новую версию; прежнее правило не переносится
на неё без публикации.

Миграция `2026092706` переносит исходный каталог и только явные
`careergrade_<stable-position-id>` привязки. Name-based legacy случаи
выводятся read-only командой `cli/grade_ladder_legacy_report.php` для
решения владельца; массового назначения по совпадению текста нет.
Переходный fallback на чтении остаётся до подтверждения и переноса всех
таких случаев. Старые заявки без версии не переписываются задним числом.

## Проверки и границы

Права проверяются в команде, записи идут под row lock/транзакцией,
повторный publish одинакового hash не создаёт версию. Деплой требует
сверки legacy отчёта, одного полного install/upgrade и Moodle DB suite
на собранном RC, затем браузерной проверки профиля, маршрута, HR,
руководителя и rollback. Source/frontend gate на черновике не является
приёмкой миграции или production.
