# Проверка Fable-аудитов по текущему Git

Дата: 2026-09-07. Метод: полный inventory дерева репозитория, чтение обязательного контекста и ADR, трассировка ключевых PHP/JS/CSS-компонентов и статическая проверка схемы. Проверены четыре приложенных документа и продуктовая стратегия из сообщения владельца. Источники приложений с SHA-256 перечислены в [SOURCES.json](SOURCES.json).

**База кода:** [e71bca2856bc0f80e39cb9ed1cee6098934e232a](https://github.com/cauf1l3d/ustarlms/tree/e71bca2856bc0f80e39cb9ed1cee6098934e232a), ветка `feature/route-position-parent-override`. В inventory `local/ustar`: 202 PHP-файла, 29 CLI-файлов; install.xml описывает 60 таблиц. В `frontend/` есть 60 файлов, включая package.json Next/React. Наличие второго frontend подтверждено, его использование в текущем production — нет.

## Границы достоверности

- `source_confirmed` — механизм или дефект подтверждён чтением указанного SHA. Это не результат запуска на production.
- `synthetic_reproduced` — минимальное воспроизведение на искусственных данных в этой проверке.
- `historical_runtime` — выводы старого изолированного стенда из release-отчётов; они не подтверждают сегодняшний прод.
- `user_reported` — пользователь показал симптом или результат установки в этой сессии.
- `needs_runtime` — требуется стенд/manifest/логи. Текущие DB counts, успешность cron, восстановимость backup, доступность contextd и все браузерные сценарии относятся сюда.

В среде аудита нет PHP CLI и Moodle DB. PHPUnit/Behat, PHP runtime, production SQL и браузерная приёмка не запускались. Никаких изменений production или DB не выполнялось. Исторические отчёты не переименованы в новую приёмку. Вывод об уязвимости ввода нельзя делать только по наличию PARAM_RAW или тройных Mustache-скобок.

## F01. Нет общей награды за прохождение точки — P0 продукта

Источник: [route_model.php: record_completion/evaluate_point](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/route_model.php#L1230-L1361), [observer.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/observer.php), [sync_uscoin.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/cli/sync_uscoin.php).

`record_completion()` записывает `local_ustar_route_progress`, не вызывает `economy::post` и не создаёт общий факт награждения. Observer завершения курса оставлен без начисления намеренно; sync_uscoin явно report-only. Специальные страницы route quiz/profile/career и проверенные провайдеры также не образуют общего контура награды. Это подтверждает отсутствие механизма «каждая точка → награда» в проверенной цепочке, а не отсутствие всех наград в системе.

Последствие: прохождение content/assessment/skill-точки может увеличить route progress без соответствующей USCOIN-награды. Исправление: R04–R06, единая серверная команда завершения с версионным правилом, provenance и идемпотентностью. Простое восстановление старого `+50 за курс` не покрывает остальные точки.

## F02. XP, достижения и соревнования считаются из разных фактов — P1

Источники: [get_dashboard.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/external/get_dashboard.php), [achievements.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/achievements.php), [submit_game_answer.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/external/submit_game_answer.php), [competition.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/competition.php).

- XP dashboard = завершённые курсы ×100 + Moodle activity completion state 1/2 ×10 + mastery XP. Route progress непосредственно в формулу не входит.
- Badges читаются из Moodle при наличии `badges_get_user_badges`; в этой цепочке нет создания отдельного достижения за route point. Наличие/вызов загрузки Moodle badge API и реальные выданные badges необходимо проверить в runtime; утверждение Fable «нет таблицы badges — нет достижений» некорректно, Moodle имеет собственную систему.
- Competition принимает `game_mastery` по опубликованным правилам и фиксированной аудитории. USCOIN намеренно отделён от leaderboard.
- В `submit_game_answer` mastery сохраняется до scoring-вызова. После сбоя scoring повторный правильный ответ уже видит mastery и не восстанавливает пропущенное событие. `catch dml_write_exception` охватывает оба действия и любую ошибку записи трактует как гонку, без проверки конкретного duplicate. Это путь потенциально потерянного scoring, подтверждённый структурой кода; инъекция сбоя на DB ещё нужна.

Исправление: R06/R08. Единое происхождение XP-наград, видимый результат, повторяемая доставка scoring и ограниченная обработка ожидаемых duplicate. Не конвертировать XP в USCOIN автоматически и не смешивать кошелёк с местом в соревновании.

## F03. Студия и runtime находятся между двумя моделями наследования — P0 продукта

Источники: [route_studio.php: POST](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/route_studio.php#L224-L635), [отключённые controls](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/route_studio.php#L974-L980), [route_scope.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/route_scope.php), [route_family.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/route_family.php).

При наличии scope runtime выбирает parent route и фильтрует его точки. В position-view студии `canedit=false`, `canoverride=false`, `canrevert=false`. При этом POST make_override/revert_parent ищет точку в child route и вызывает прежнюю материализацию из `route_family`. `points_for_position` фильтрует только точки переданного маршрута, не реализует замену parent на scoped override из ADR-0004.

Дополнительный край: отсутствие активных scope rows означает «всем». Если будущий revert просто деактивирует последнюю scope-запись override, он может неожиданно стать общим. Нужен отдельный контракт unscoped legacy vs reverted/override. В presenter отсутствующие confirmed/proposed тоже показываются как all; это не должно скрывать отказ runtime для иных состояний.

Исправление: R02, общий resolver и команды согласно существующему ADR. Не включать старые кнопки одним CSS/boolean-патчем. Полная матрица в [ROUTE_STUDIO_ACCEPTANCE.md](ROUTE_STUDIO_ACCEPTANCE.md).

## F04. Сохранение/публикация могут завершиться частично — P0 инженерии

Источник: [update_point](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/route_model.php#L241-L263), [create_version](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/route_model.php#L444-L590).

POST save_version сначала вызывает `update_point`, который коммитит свою транзакцию, затем отдельно `create_version`. Создание версии выбирает latest+1 без общей блокировки точки; unique point/version ограничивает дубликаты, но не делает весь save атомарным. После INSERT версии ошибка наследования assessment-policy подавляется через debugging. Таким образом операция может сообщить/оставить неполный результат при сбое позднего шага.

Исправление: R03 — одна команда, per-point lock, revision/stale validation, транзакция metadata+version+required policy+scope; ошибки обязательной политики блокируют публикацию. Тестировать конфликт двух редакторов и принудительный отказ каждой записи. Дополнительная точка проверки R05: lifecycle PASS в `for_user` может вызывать `record_completion` отдельной веткой; нельзя реализовать награду только внутри evaluated-ветки.

## F05. Git, runtime и AI-контекст ещё не сведены — P0

На старте аудита main не содержит context/ и AGENTS.md. Feature содержит контекст с git snapshot `109b94b…` от 08:01, но проверяемый HEAD уже `e71bca2…`. README сообщает baseline 1.5.1 и старые пути. Это датированные сведения, а не доказанный текущий release manifest.

Пользователь в сессии показал mount и фактический путь с **двумя public**; `scripts/refresh_context.sh` жёстко записывает путь с одним public, а затем сообщает успешное обновление. [Ручной code_map](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/context/code_map/dependencies.yaml) ссылается на `classes/uscoin.php` и `route_runtime.php`, отсутствующие в inventory проверенного plugin; реальный economy-класс называется `economy.php`.

`scripts/build_code_map.sh` строит список «таблиц» поиском строк в PHP, а не разбором XMLDB. `build_context_index.py` включает собственный output в обход context/, поэтому после перезаписи записанный hash самого индекса становится устаревшим. Источник root также жёстко задан.

Исправление: R00/R17 — release manifest, обнаружение корней по mount, явное время и источник факта; ссылки проверяются по tree; schema inventory из XMLDB; output исключён из своего индекса. Публикация roadmap с входом из main закрывает обнаружимость плана, но не закрывает production drift.

## F06. CI существует, но не защищает эту базу — P0

Источник: [workflow](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/.github/workflows/ustar-review-gate.yml). Trigger: workflow_dispatch и push только `ustar-final-audit-release`, pull_request отсутствует. Assertions ожидают version/XML `2026082705`, тогда как plugin version = `2026082730`, XML VERSION = `2026082729`. Само различие plugin/XML не доказывает ошибку схемы; жёсткая проверка 2705 на этой базе устарела.

API GitHub вернул 34 исторических workflow runs. Последний из запрошенных пяти: [успешный run 33071721342](https://github.com/cauf1l3d/ustarlms/actions/runs/33071721342) от 2026-08-27 на `156adb5…`, не на audited SHA. В plugin отсутствует tests/ с PHPUnit/Behat; есть CLI проверки, включая реальный `test_materials_library.php` с assertions и изоляционным guard. Поэтому «совсем нет автоматических проверок» неверно.

Исправление: R01 — перенести полезные assertions в действующий suite, проверить актуальные branches/PR trigger, Moodle bootstrap и PostgreSQL DB, собирать AMD, проверять схему установкой и обновлением. Не подменять meaningful tests grep-проверкой наличия функции и не ставить `|| true` на обязательные этапы.

## F07. Миграции привязаны к конкретным данным — P0 воспроизводимости

Источник: [upgrade.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/db/upgrade.php#L2266-L2284). В upgrade 2026082710 запрашивается route id=49/familyid=1 с MUST_EXIST. Рядом преобразования конкретных point IDs и seeded department code. Это не универсальная миграция для любой старой инсталляции. XML описывает семейства и scope, но install-path и upgrade-path требуют настоящего сравнения на DB.

Исправление: R09. Сначала перечень поддерживаемых исходных версий и проверка копии текущей БД. Новые миграции — с preflight, устойчивыми ключами и проверками происхождения данных. Исторические блоки не удалять; если требуется исправить ещё поддерживаемый старый путь, отдельно документировать совместимый guard и тест на соответствующем fixture. Не заменять неизвестный positionid произвольной default-должностью.

## F08. Видимые UX-дефекты имеют конкретную причину — P1, быстрый выпуск

Источники: [positions.php: occupancy](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/positions.php#L322-L331), [material_manage.css](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/material_manage.css), [theme materials](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/theme/ustar/scss/_materials.scss).

`$positionid` выбранного запроса перезаписывается должностью каждого сотрудника при подсчёте occupancy. Затем эта переменная участвует в модели должности/лестнице. Это подтверждённая причина жалобы пользователя; исправление — отдельная локальная переменная счётчика. В CSS реально есть 7–9 px и muted-поверхности; реальный computed contrast и каскад проверяются в браузере.

Оргсхема, подразделения команды, фильтры и клики к обученности — предыдущие запросы пользователя, отражённые в [STATE.yaml](STATE.yaml). Подготовленный единый пакет не равен Git-коммиту или доказанному деплою. Группировка UI «генеральный → блоки → отделы» сама по себе не меняет кадровые полномочия и фактические связи reporting.

## F09. Видимость команды и кадровые инварианты требуют консолидации — P1

Источники: [organization_model.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/organization_model.php), [org.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/org.php), [get_team.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/external/get_team.php), [department_learning.php](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/moodle/local/ustar/classes/department_learning.php).

API get_team использует explicit direct_reports, page department_learning — manager_scope из staffplaces/assignments. Это различные контракты, они могут быть намеренными; ошибку раскрытия чужих данных без role-fixture не заявляем. Требуется явное сравнение и единый набор правил для direct vs full subordinate scope.

`staffing_requests::review` имеет транзакцию, но чтение pending-заявки не берёт отдельный lock; `assign_hire` проверяет свободное место и затем вставляет primary assignment без собственной защиты конкурентного выбора. `adaptation_service::assign_from_request` тоже имеет транзакцию и проверку заявки. Это не «нет транзакций нигде», а конкретные гонки для DB-тестов R13. Политика исключительности PRIMARY и временного ACTING должна учитывать интервалы, а не лишь status.

R10/R12/R13: сначала права и инварианты, потом миграция справочников. Не удалять reporting до проверки ручных override, consumers и истории.

## F10. contextd не ограничивает чтение файлом внутри context — P0 при доступном MCP

Источник: [server.py: get_context_file](https://github.com/cauf1l3d/ustarlms/blob/e71bca2856bc0f80e39cb9ed1cee6098934e232a/harness/ustar-contextd/server.py). Путь соединяется с ROOT без resolve/containment/allowlist. На извлечённых через AST функциях проверенного source выполнен минимальный тест с искусственным файлом: чтение за пределами тестового root возможно. Секреты и реальные внешние файлы не читались.

Transport, настройки запуска и внешняя экспозиция не установлены; это не утверждение о доступном из интернета endpoint. Исправление R16: разрешённый корень/типы, canonical-path containment, symlink check, лимит размера, тесты отказов и соответствующая текущему transport авторизация. Новый сервер не нужен.

## F11. Privacy/операционные доказательства — P1

В tree отсутствует `classes/privacy/provider.php`. Это технический пробел интеграции с Moodle Privacy API; вывод о соответствии конкретному закону по этому признаку не делается. Нужны inventory PII, экспорт, минимизация, retention и согласованный режим сохранения исторических ledger/evidence.

`route_tester` уже проверяет siteadmin, маркировку тестового пользователя и использует sandbox guard. Нельзя описывать его как произвольное удаление любых сотрудников без ограничений. Тем не менее отделить среду теста, проверить все входы и отказ для реальных аккаунтов необходимо.

CPU/контейнеры из старого облачного отчёта не описывают доказанно нынешний сервер. Прежде чем покупать инфраструктуру: измерить p95/DB queries/cron lag/disk, проверить backup restore на отдельной изолированной копии и запрет исходящих реальных уведомлений на stage. Задачи R14/R15/R19.

## Что в четырёх внешних документах нельзя выполнять буквально

| Тезис/фрагмент | Результат проверки |
|---|---|
| «В economy нет транзакции ledger↔balance» | Устарел: есть per-key/per-user locks, транзакция, FOR UPDATE, spend и reversal; нужна регрессия, а не замена |
| «Нет CI и автоматических проверок» | Нет нормального suite актуальной ветки; старый workflow и 29 CLI есть |
| «Нет исходников frontend» | В этой базе frontend есть; назначение в prod не подтверждено |
| «Четыре Org-модели, всё объединить удалением» | Есть конкурирующие контракты, но также разные сущности и read models; удаление projection проблему прав не решает |
| «Skill evidence и evidence record — один дубль» | Первое содержит определения требований, второе факты; миграция обязана сохранить оба смысла согласно ADR-0003 |
| «Freeze gamification» | Не соответствует текущему явному приоритету владельца: маршрутные награды и достижения — S2 |
| «8 недель / 44 часа на ядро / 500 RPS / 80% coverage» | Не проверенные оценки и произвольные targets; заменить критериями сценариев и измерениями |
| Shell restore из `prod-*.sql.gz`, stage-данные, симлинк на весь Moodle | Не готовый runbook: неоднозначный dump, окружения/пути и полный Moodle bootstrap не проверены; нужен отдельный restore с manifest, изоляцией и отключёнными внешними эффектами |
| CI с `composer install` внутри plugin и `|| true` | Наличие plugin composer config и bootstrap не доказано; ошибки обязательных проверок не должны подавляться |
| Удалить старые миграции, поменять все IDs на INT, удалить PK id у balance | Не требуется текущими ADR; несёт риск истории/совместимости Moodle; не принято этим roadmap |

## Итоговая оценка

Фундамент можно развивать поступательно: версионные точки, атомарный ledger, read-only управленческая сводка, scoped routes, адаптация и assessment-policy уже представлены в коде. Основные срочные разрывы находятся между этими компонентами и в воспроизводимости выпуска. Поэтому задачи R00–R09 приносят более непосредственный эффект production, чем новая универсальная архитектура или инфраструктура ИИ.
