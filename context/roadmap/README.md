# USTAR: roadmap надёжного продукта

Дата базовой проверки: **2026-09-07**. Текущие статусы находятся в [STATE.yaml](STATE.yaml) и [BACKLOG.yaml](BACKLOG.yaml); этот документ объясняет порядок работ.

**Ближайшая цель: HR публикует корректный маршрут, сотрудник проходит каждую доступную точку, получает объяснимую награду, руководитель видит тот же результат. Изменение выпускается из Git с проверкой и откатом.**

Это объединяет инженерный порядок с пользовательским результатом. Переписывание всей системы, новые интеграции и перенос интерфейса на SPA не являются предварительными условиями.

## Где мы сейчас

- Стадия: **S0 — сверка релизной базы и стабилизация**. Production используется, но полная приёмка актуального SHA не предъявлена. Это не заявление о неработоспособности всего продукта.
- Проверенная база кода: [`feature/route-position-parent-override`, `e71bca2856bc0f80e39cb9ed1cee6098934e232a`](https://github.com/cauf1l3d/ustarlms/tree/e71bca2856bc0f80e39cb9ed1cee6098934e232a).
- На момент проверки `main` содержала старую базу `5443bf5ab2c000a0fc019d3b0b30dcff0a60a7ff`. Публикация этих документов не переносит в `main` прикладной код из feature-ветки и не меняет production.
- Контекст и ADR уже существуют в feature-ветке. Нельзя создавать вместо них новую архитектуру по тексту внешнего аудита.
- Текущая задача следующего агента: **R00 — сверить Git, release-пакеты и фактически установленные файлы**. Допустимая работа без runtime-доступа: подготовка diff, manifest и проверки на изолированной копии; отсутствие runtime не разрешает объявлять релиз подтверждённым.

## Порядок исполнения

Оценки ниже — диапазоны инженерной работы одного исполнителя с рабочим Moodle-стендом, без ожидания доступа и бизнес-приёмки. Это ориентиры, не обещание календарных дат. Выход из этапа определяется проверками.

| Этап | Задачи | Ориентир | Условие перехода |
|---|---|---|---|
| **S0. Воспроизводимая база** | R00, R01, R16; начать R09 и R15 | 3–7 рабочих дней | База и drift известны; изолированный стенд поднимается; критический suite действительно запускается; чтение contextd ограничено |
| **S1. Рабочая студия и быстрые UX-исправления** | R02, R03, R07; завершить R09 | 1–2 недели | Один опубликованный состав в студии, кабинете и сводке; сценарии из [приёмки студии](ROUTE_STUDIO_ACCEPTANCE.md) проходят |
| **S2. Полная геймификация маршрута** | R04, R05, R06, R08; продолжить R15 | 2–3 недели | Все реально поддерживаемые типы точек проходят проверку наград; повторы не умножают баланс; достижения видны |
| **S3. Порядок внутри доменов** | R10–R14, R17, R19; R18 после R05/R06 | 3–6 недель небольшими PR | Единые правила доступа и evidence; ключевые use case вынесены из контроллеров; мониторинг и Privacy API проверены |
| **S4. Развитие продукта** | R20 | После S2 и нужных частей S3 | Профиль должности и кабинет руководителя опираются на достоверные факты; интеграции имеют отдельные контракты |

Это не жёсткая последовательность всех задач: R04 можно проектировать во время R02, R07 не ждёт большой миграции оргструктуры. При обнаружении воспроизводимого инцидента с потерей данных или доступом он получает приоритет выше планового этапа.

## Первые конкретные поставки

1. **R00 + R01 + R16:** перечень проверенных файлов и версий, перечень ещё не закоммиченных патчей, обязательный CI для текущей ветки, минимальный DB-suite и ограниченное чтение contextd. Это делает следующие правки проверяемыми.
2. **R07:** исправить переменную выбранной должности; перенести подготовленные исправления материалов и оргсхемы в Git после сравнения с фактическими файлами. Закрыть видимые пользователю дефекты без ожидания переписывания Org-домена.
3. **R02 + R03:** довести редактирование общего шага, исключения для должности, возврат и атомарную публикацию. Показать HR опубликованное состояние и черновик отдельно.
4. **R04 + R05 + R06:** выпустить целиком сценарий награды: серверное подтверждение → право на награду → USCOIN/XP → карточка результата → достижения. Один CSS-эффект или изменение баланса вручную не закрывает эту поставку.
5. **R08 + R15:** проверить игровую студию, повторы ответов, восстановление потерянного scoring-события, cron и алерты на незавершённые начисления.

## Как выполнять рефакторинг

Рефакторить по пользовательским операциям, сохраняя публичные вызовы совместимыми на переходном этапе:

| Участок | Сначала зафиксировать поведение | Затем выделить |
|---|---|---|
| `route_model.php` | Матрица условий, версии, scope, expiry, read-only | Общий resolver точек; чистый evaluator; явная команда фиксации результата; presenter |
| `route_studio.php` | Save/publish/override/revert/reorder, stale edit, права | Сервис редактирования маршрута с общей транзакцией; контроллер оставляет параметры, авторизацию и render |
| `target_core.php` + `evidence.php` | Что является фактом и что является правилом; revoked/expired | Фасад записи evidence и единое чтение действительности факта согласно ADR-0003 |
| `organization_model.php` + `org.php` | PRIMARY/ACTING, доступ к команде, реальные линии подчинения | Единый контракт видимости; позже — миграция каталогов согласно ADR-0002 |
| `adaptation_service.php` | Daily/final/extension/HRD, роли, повтор запроса | Команды переходов и read model; существующие события и история сохраняются |
| `content_admin.php` и страницы материалов | Publish/version/ACL/library/download | Сервис контентных команд и presenter; CSS остаётся представлением |

Само наличие статических методов или `$DB` не доказывает дефект. Не вводить Repository для каждой таблицы, новый EventBus или новые learning-plan таблицы без потребности конкретной операции. Критерий результата — контролируемые зависимости, транзакции и меньше регрессий, а не произвольное число строк в файле.

## Геймификация — обязательная часть ядра

Утверждённое пользователем требование: **каждое новое подтверждённое прохождение доступной точки награждается и заметно сотруднику**. Геймификация и достижения не замораживаются.

- XP показывает развитие, USCOIN — расходуемую награду, очки соревнования — результат по правилам конкретного сезона. Это разные величины.
- Повторный HTTP-запрос, refresh, перенос старого результата на новую версию и просмотр руководителем не являются новым прохождением.
- Новая реальная пересдача после expiry должна иметь отдельный подтверждённый цикл. Текущая уникальность progress по `userid/pointid/versionid` сама по себе этого не моделирует.
- В студии заранее видно условие завершения и награда. После прохождения — фактическое начисление, причина, новый прогресс и следующая точка. История переживает обновление страницы.
- Сначала минимальный рабочий набор достижений и один игровой формат end-to-end; расширение форматов после исправления их общего контура.

Подробная спецификация: [REWARD_CONTRACT.md](REWARD_CONTRACT.md). Числа наград предложены для пилота и не являются действующими настройками production.

## Что из Fable принять и что пересмотреть

Принять: сокращение ответственности контроллеров, критические интеграционные тесты, воспроизводимые релизы, развитие кабинета руководителя, роль должности как понятной точки входа, факты из работы в будущем.

Пересмотреть:

- Транзакционная экономика и CI **уже есть**, но CI устарел и не защищает текущую feature-ветку. Чинить конкретный пробел, не строить заново.
- `company_hierarchy` — представление, `staff_place` — место, `assignment` — назначение, `skill_evidence` — описание требования. Они не становятся дублями только из-за связи с сотрудником.
- Не удалять `coin_accounts`, reporting, progress или evidence по признаку «пусто в августовском dump». История и актуальные потребители должны быть сверены.
- Не менять все `positionid` на INT и не вводить двустороннюю синхронизацию JSON↔DB на первом этапе. Нужны устойчивые ID, один писатель, отображение старых ключей и dry-run.
- Не обрезать `upgrade.php` по номеру версии без перечня поддерживаемых upgrade-path и проверки восстановления.
- Не переносить весь UI на SPA, не устанавливать SSO/Telegram/RAG и новый contextd вместо исправления текущих сценариев.
- Не использовать предложенные Fable shell/SQL/CI-фрагменты как готовые production-runbook. В них есть неподтверждённые пути, зависимость от несуществующих файлов и шаги, не проверяющие нужный результат.

## Чем измерять эффект

Сначала измерить baseline на текущем стенде; не придумывать текущие проценты.

| Метрика | Цель поставки |
|---|---|
| Награждённые eligible completion / все eligible completion | 100% после обработки очереди; нет потерянных начислений |
| Число повторных ledger grants одного entitlement | 0 |
| Совпадение точек/версий/статусов в студии preview, кабинете и read-only сводке | 100% в тестовой матрице |
| Ошибки save/publish и потеря содержимого формы | Нет частичных сохранений; recoverable ошибки показаны пользователю |
| Critical smoke нового release SHA | Все обязательные сценарии прошли на изолированном стенде |
| Прохождение/начисление, видимое сотруднику | Результат синхронно или явное «начисляется» с автоматическим завершением; целевой async lag ≤60 с на пилоте |
| Скорость кабинета и команды | Измеренные p50/p95 и SQL-count на согласованном количестве пользователей; отсутствие регрессии >20% без объяснения |

Time-to-productivity, реальные допуски и связь с продажами появятся после определения бизнесовых событий. Нельзя заменять их количеством открытых страниц.

## Как продолжать любой ИИ

Начать с [START_HERE.md](../../START_HERE.md), [STATE.yaml](STATE.yaml), [ACTIVE.md](../tasks/ACTIVE.md) и [AGENT_PROTOCOL.md](AGENT_PROTOCOL.md). Выбрать первый готовый ticket, прочитать его evidence и ADR, реализовать ограниченную поставку, приложить проверки, обновить статус в том же изменении. Документ «всё работает» без SHA и runtime-evidence не закрывает задачу.
