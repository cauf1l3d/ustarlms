# ADR-0006 · Явное полномочие решения HRD по адаптации

Дата: 27.09.2026. Статус: предложено в кодовом PR G01; runtime-приёмка открыта.

## Контекст

`adaptation_service::is_hrd_actor()` пытался вывести роль HRD из
`structure::resolve_user()['role']` или профиля должности. Оргструктура
возвращает роль в управленческой иерархии, не независимое полномочие
на решение эскалации. `local/ustar:hrmanage` одновременно выдаётся
обычному HR, поэтому одна эта capability не отделяет HRD.

## Решение

Новая системная capability `local/ustar:manageadaptation` проверяется
при каждом HRD-решении. Она независима от названия должности, отдела,
`hrmanage` и `approveregistration`. Актор обязан быть действующим,
совпадать с реальным `$USER`, иметь `local/ustar:use` и не находиться
в режиме «Просмотр как». Moodle siteadmin сохраняет штатный полный
доступ при действующей учётной записи.

При свежей установке и upgrade capability получает роль `ustar_hrd`
и `ustar_superadmin`; `ustar_hr` её не получает. Ручные назначения
ролей пользователям не переписываются. Если действующий HRD имел
доступ лишь из-за текста поля должности без соответствующей роли,
оператор назначает нужную явную роль после проверки: автоматического
повышения по строке/подразделению нет. Upgrade не обрабатывает
исторические решения и не меняет их автора.

Отдельно HR может сохранить контактные данные действующего сотрудника
без должности. Нормальные состояния resolver для такого человека:
пустой список конфликтов при отсутствии истории назначений и
`no_active_primary_assignment` после завершённой PRIMARY. Оба
состояния означают «должность не назначена», но любые другие конфликты
по-прежнему запрещают ложное сообщение об успешном сохранении.

## Проверка и границы

Регрессия проверяет обычный HR без capability, действующего HRD с
явным правом, приостановленного актора и сохранение без должности
с историей/без неё. В общем Moodle DB suite будущего frozen RC
проверяются fresh install, upgrade, роли и фактическое решение.
Перед deployment сверяется, что участники очереди HRD имеют роль
`ustar_hrd` либо отдельно выданное полномочие; персональные имена
и назначения не публикуются в Git.
