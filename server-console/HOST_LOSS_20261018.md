# Как заметить отключение server1 без собственного второго сервера

Запрос владельца18Oct18:55МСК. Это схема подключения, не выполненная установка внешнего мониторинга. Порт8443 и Академию наружу открывать не требуется. Исходящий Xray бота остаётся только для api.telegram.org; правила VPN/DNS/firewall не меняются.

## Что возможно сейчас

Пока server1 работает и Telegram достижим, локальный notifier сообщает о сбое контейнера, HTTP, cron, дисков, сборщика и очереди. При потере интернета сообщения остаются в локальной очереди. Если выключены питание, ОС или сеть самого server1, его бот тоже не работает: собственный таймер не сможет отправить сообщение об этом.

Нужна независимая точка, которая заметит **отсутствие** исходящего сигнала. Ею может быть готовый managed heartbeat-сервис, например Healthchecks.io, вместо собственного дополнительного VPS. Сервис ожидает HTTPS ping и сам отправляет тревогу через свою Telegram-интеграцию и email. Не передавать ему токен существующего USTAR-бота и не запускать второй getUpdates для того же бота.

## Два сигнала и значения

| Сигнал | Когда отправлять | Период / допуск | Что подтверждает |
|---|---|---|---|
| `server1-alive` | Отдельный минимальный systemd timer успешно исполнился | 60с / 180с | Хост исполняет код и имеет исходящий HTTPS к наблюдателю |
| `academy-local` | Только свежий результат существующего локального HEAD: status=ok и age<=45с | 60с / 180с | Сборщик и локальный HTTP отвечают; внутренние права/SCORM/полный вход этим не проверены |

Задержка тревоги — примерно период+допуск, то есть до4мин от последнего сигнала плюс доставка. Лучше называть её «пропал heartbeat», а не «сервер выключен».

| Что наблюдаем | Обоснованный вывод | Что остаётся неизвестным |
|---|---|---|
| alive приходит; academy нет | Хост достигает наблюдателя; локальная HTTP-проверка/сборщик не подтверждены | Причина приложения, БД или сборщика по heartbeat не различается |
| Оба пропали | Потерян путь server1→наблюдатель либо исполнение таймеров | Питание, зависшая ОС, LAN, ISP, DNS, TLS или сам сервис |
| Оба приходят; локальный бот молчит | Heartbeat-канал доступен, канал Telegram/worker требует проверки | Это не полный отказ интернета |
| После разрыва сигналы возобновились | Связь с наблюдателем восстановилась | Время и причина локальной аварии уточняются по сохранённым событиям |

Для различения «упал server1» и «упал интернет всего офиса» нужен дополнительный независимый признак. Можно использовать уже существующий постоянно включённый офисный ПК/NAS с собственным heartbeat (нового сервера не нужно): его сигнал приходит, а server1 нет — проблема локальнее server1; оба пропали — общий путь вероятнее. Это всё ещё гипотеза, не доказательство отключения питания. Роутер/UPS с телеметрией позволяют уточнить причину; спящий телефон или ноутбук не считается надёжным наблюдателем.

## Порядок подключения

1. В своём аккаунте сервиса создать два простых check с указанными периодом и допуском, включить Telegram и независимый email, проверить Test notification. Названия без персональных данных/внутренних адресов.
2. Сохранить секретные ping URL только на сервере в root-owned0600 файле, вводом с терминала без вывода в чат, историю команд или Git. URL работает как ключ: утечка позволяет подделать heartbeat.
3. Проверить исходящий HTTPS именно к домену наблюдателя с server1. Доступ к api.telegram.org через Xray эту проверку не заменяет. Если сервис заблокирован, подобрать доступный managed endpoint; не расширять Telegram-only proxy до общего VPN.
4. Подготовить отдельный минимальный oneshot/timer, непривилегированный UID, TLS verification, no redirects, timeout10с, один HTTPS POST без body/логов/метрик. HTTP200 с точным ответом `OK` — успех; ошибки только фиксированным кодом без секретного URL. Второй сигнал читать из root-collector snapshot по фиксированному пути; при stale/no_data сигнал успеха не слать. Существующий console collector/timer не превращать в бесконечный сетевой запрос.
5. Подключать только после получения URL локально. До этого observer в пульте остаётся `не подключён`. Внешний сервис не даёт доказательства проверки роли, восстановления или RTO.
6. Проверить нормальный сигнал, затем **остановить только новый heartbeat timer**, не сервер/Академию. Дождаться внешней тревоги, вернуть timer и получить recovery. Отдельно проверить отсутствие свежего academy snapshot. После этого записать фактическое время и получателя приёмки без секретных URL.

Никакой платный план/внешний аккаунт или передача телеметрии в этой поставке автоматически не создаются. Следующий практический шаг для активации — выбрать сервис и локально получить два ping URL; саму доступность с server1 затем проверяет владелец.
