# Границы системы

1. Moodle core владеет пользователями, auth, capabilities, LMS completion, native messages и File API. Core не изменять без отдельного согласованного решения.
2. `local_ustar` владеет корпоративными бизнес-правилами. Controllers и theme не должны становиться вторыми источниками правил. При изменении проверить service, readers, writers, scheduled tasks и прямые URL.
3. `theme_ustar` отвечает за представление. Скрытие кнопки не заменяет серверную проверку права. Название должности и view-as не предоставляют полномочие.
4. Schema задаётся `db/install.xml`, переход — `db/upgrade.php`. Сохранять историю, explicit migrations, fresh/upgrade/repeat parity. Downgrade файлов после DB upgrade не является откатом.
5. Read models не должны скрыто исправлять организацию, начислять награды или запускать cron. Проверять старые probes до запуска: имя audit/check не гарантирует отсутствие записи.
6. Новый мобильный клиент — потребитель существующих доменов через проверяемый API. Не создавать вторую базу сотрудников, сообщений, прогресса или кошелёк. Конкретный transport/auth/offline contract должен пройти отдельный ADR.
7. Production — внутренний контур. DNS, HTTPS, VPN, proxy, сертификаты и способы распространения приложения требуют измеренных фактов и согласованного решения. Публикация Git не открывает сервер в интернет.
