# Рефакторинг USTAR — этап 1 из 6

База приложения: `378d397152a8c83f8b0d046e2e561ab2732d6b02`, ветка `integration/ustar-20260919`.
Это инженерная основа перед изменением регистрации, оргструктуры и HR-интерфейса. Production не изменён.

## Изменения

- Пустой стандарт должности учитывается как «не настроен», а не квалификация 100%.
- `route_model::for_user` в preview читает сохранённое состояние. Синхронизация assessment в preview не вызывает provider и не пишет runtime; команды remediation запрещены.
- Удалять историю можно только у собственной зарегистрированной Route Tester учётки администратора. Реальные сотрудники и подмена actor запрещены на уровне сервиса.
- Тестовые учётки исключены из начисления маршрутных наград. Повторные циклы реальных сотрудников будут исправляться в отдельном этапе экономики.
- Frontend: Next 15.5.25, ограничение тела запроса, проверка Origin, защита служебных параметров Moodle, шифрованная сессия с серверным сроком 12 часов и обязательным секретом. Старые cookie перестают работать; потребуется повторный вход.
- CI проверяет текущий код PR, а не исторический release-каталог: синтаксис, структура, регрессии, frontend и отдельный Moodle/PostgreSQL.
- Стенд ставит baseline, обновляет приложение, повторяет upgrade и сравнивает схему с чистой установкой. PHPUnit проверяет реальные таблицы и сервисы на синтетических пользователях.
- Manifest связывает Git SHA, хеши исходников и lock-файлы. Preflight требует явный commit и может останавливать выпуск при расхождениях.
- Реальный DB-прогон обнаружил ошибку чистой установки baseline: initial roles назначались до регистрации capabilities. В новой версии порядок исправлен. Убрано недопустимое XMLDB `DEFAULT=""` у `route_testers.positionid`: Moodle уже нормализовал его в отсутствие default, поэтому физическая схема не меняется.

## Воспроизведение

```sh
python3 scripts/ci/prepare_stage.py
mkdir -p artifacts
docker compose -f tests/stage/compose.yaml build --pull
docker compose -f tests/stage/compose.yaml up --abort-on-container-exit --exit-code-from runner
docker compose -f tests/stage/compose.yaml down --volumes
```

Нужны Docker Compose и доступ к реестрам только при сборке. Во время тестов внутренняя сеть не имеет внешнего доступа, портов на хосте нет. Используются отдельная БД, префиксы `stage_`, `fresh_`, `phpu_`, временные каталоги и фиктивные реквизиты. Production config, БД и moodledata не копируются. Образы указаны по версиям; CI сохраняет фактически полученные image IDs/digests. Полная побайтовая воспроизводимость apt-зависимостей не заявляется.

Для upgrade-fixture сначала устанавливается Moodle core, затем регистрируются capabilities старого plugin и устанавливается неизменённый baseline. Это явная подготовка старой системы, а не успешная чистая установка исторического SHA: её дефект воспроизведён в CI run 35512180537. Кандидат проходит отдельную чистую установку без подготовки capabilities; его `db/install.php` обязан работать самостоятельно.

## Выпуск и откат

1. Дождаться зелёного `USTAR review gate / gate`, проверить DB-логи и manifest конкретного SHA. Назначение required check в настройках GitHub отдельно; сам workflow не меняет branch protection.
2. На production выполнить только read-only preflight:
   `python3 scripts/production_manifest.py --repo REPO --moodle-root MOODLE_PUBLIC --commit 378d397152a8c83f8b0d046e2e561ab2732d6b02 --require-match --output-dir NEW_AUDIT_DIR`.
   Код 2: неполный снимок; 3: расхождения; оба останавливают автоматическое применение. Остаточные файлы разбираются явно, не удаляются автоматически.
3. До применения сохранить согласованный комплект: БД, moodledata, исходники, защищённые config/env, версии образов. Восстановить его на изолированном сервере и проверить вход, файлы, маршрут и ledger. Синтетический CI не заменяет эту проверку.
4. Проверить frontend `SESSION_SECRET` (случайный, минимум 32 байта), `APP_ORIGIN` (точный публичный origin), `MOODLE_URL`. Пересобрать образ. Пользователи войдут заново; серверной таблицы индивидуального отзыва сессий этот этап не добавляет.
5. Применять plugin/theme только из проверенного SHA, запустить штатный Moodle upgrade и purge caches. Проверить HR, сотрудника, руководителя, Route Tester и вход frontend на stage перед production.
6. При неудаче остановить запись и восстановить согласованный комплект целиком. Не понижать Moodle plugin version вручную и не откатывать только файлы поверх новой БД.

## Ограничения этапа

Не заявлены: доступ к живой академии/учётке Лейлы, production restore, runtime-роли production, миграция кадровых данных, новая регистрация, единый HR-пульт, полное устранение write-on-read во всех доменах, новая reward cycle identity, полный privacy provider. Это следующие этапы и отдельные acceptance gates.

Рискованные CLI (`reset`, `migrate`, `seed`, `apply`, а также исторические `check/probe`) не запускаются на production этим pipeline. Существующие утилиты не считаются безопасными по названию. В тестовом стенде выполняются только перечисленные команды core install/upgrade/phpunit и read-only снимок схемы.
