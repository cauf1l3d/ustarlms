Дата: 26.10.2026 (Москва). Статус: подготовлено к согласованию; реализация и деплой не выполнены.

## Задача владельца

Перенести существующий редактор https://ustar-rc-editor-oct19.ochrehippo10.chatgpt.site/ в Академию, сохранив его внешний вид, форм-фактор и возможности. Вход из «Материалов» (`materials.php?theme=ustar`); единое рабочее пространство для имеющих действующее право редактирования. Курсы любых подразделений, импорт, создание, редактирование и сохранение в материалы. Все рабочие данные и зависимости внутри контура; никакой авторизации ChatGPT.

## Подходы

1. **Рекомендуется: перенести существующий HTML/CSS/JS в native local_ustar и подключить Moodle backend.** Максимальная точность интерфейса; повторное использование каталога, capabilities, File API, SCORM runtime. Это единственный подход, удовлетворяющий одновременно сохранению редактора и работе внутри контура.
2. iframe внешнего сайта не соответствует требованию локальности, сохраняет внешнюю авторизацию и отдельное хранилище; исключён.
3. Новый редактор с нуля или legacy Next.js увеличивает объём и риск визуальных расхождений, противоречит текущей native архитектуре; исключён.

Выбор первого варианта — инженерное предложение, не зафиксированное согласование владельца.

## Пользовательский сценарий

В «Материалах» действующая кнопка студии открывает общую «Студию курсов». Слева выбор проекта и экраны, в центре редактируемый лист и панели форматирования, справа свойства экрана/оформление. Сохраняются текстовые стили, размеры/цвета, акценты, таблицы, фотографии, галерея, пользовательские шрифты, источники, порядок/дублирование экранов, undo/redo и предпросмотр компьютера/телефона.

Убирается специализация «РЦ» из общих названий; существующие коды и содержание RC-курсов не меняются. Добавляются выбор доступной папки материалов и переход к существующим настройкам аудитории. Аттестации остаются в действующем Moodle Quiz-конструкторе; учебная самопроверка не превращается в аттестацию.

- Автосохранение: общий серверный черновик материала с видимым состоянием сохранения. Первое сохранение уже создаёт draft в текущем каталоге; отдельного невидимого хранилища проектов нет.
- «Сохранить проект»: переносимый файл исходника с ресурсами, как сейчас.
- «Экспорт SCORM»: автономный SCORM 1.2.
- «Сохранить в материалы»: фиксирует редакцию общего черновика и собирает соответствующую SCORM-активность через существующий сервис. Затем открывает карточку материала для настройки аудитории и явной публикации.
- Сохранение не публикует материал и не назначает обучение автоматически. Изменение опубликованного курса не изменяет его пакет на лету; пользователь явно возвращает материал в черновик по текущему контракту либо создаёт копию. Исторические активности/попытки сохраняются. Возврат в черновик снимает текущую публикацию и может прервать доступ; это не скрытый draft поверх опубликованного курса. По умолчанию для работы без снятия публикации предлагается копия. Открытие и автосохранение никогда автоматически не выполняют unpublish.

## Права и scope

Сохранить существующее разделение: вход в каталог требует `local/ustar:hr`, управление студией — `material_studio::can_manage()` / `capabilities::HR_WRITE` (активный реальный пользователь с `hrmanage`/`admin` либо siteadmin). Само право просмотра материалов не даёт редактирования. Не расширять роли автоматически.

Рабочее пространство общее для авторов: текущий `list_for_author()` возвращает все blueprints после глобального HR_WRITE. Подразделенческого author scope в этом сервисе не выявлено; перенос сохраняет именно этот глобальный management scope. Аудитория опубликованных материалов остаётся в `local_ustar_content_access` и существующем `content_admin`; подразделение/должность не образуют параллельный ACL. Для изменения существующего материала сохраняются его папка и access rules; для нового обязателен просмотр аудитории перед публикацией, без неявной публикации «всем».

Каждый endpoint и выдача ресурса повторно проверяют реального actor, активность, capability и применимый scope. View-as не даёт записи. POST требует sesskey. Идентификаторы actor из клиента не принимаются. Прямые URL файлов и API не обходят ограничения.

## Источники и хранение

Сохранить канонические `local_ustar_content` + `local_ustar_content_blueprints`, расширив versioned source JSON форматом визуального проекта. Не создавать вторую библиотеку опубликованных курсов и второй completion store. Редактируемый общий проект связан с content ID; существующий `sourceversion` — серверная ревизия. Клиентская revision для undo не является основанием авторизации или контроля конкуренции.

Изображения/шрифты — Moodle File API с отдельной областью файлов исходника и привязкой к blueprint/source revision; JSON содержит ссылки и хеши, не многомегабайтные base64. Переносимый экспорт собирает ресурсы обратно. Source history и audit сохраняют редакцию/автора/время, но не дублируют бинарные ресурсы в журнале.

На первом срезе новые таблицы не планируются: существующие content/blueprint/Workflow events + File API. Если проверка реализации покажет необходимость schema migration, отдельно зафиксировать её и обеспечить install/upgrade/repeat parity. Версию плагина повысить при выпуске, не менять Moodle core/theme parent.

Сохранять через блокировку `studio:<contentid>`, expected source revision, expected `content.timemodified` и транзакцию. Проверять оба значения под блокировкой: аудитория/папка/статус могут измениться без новой sourceversion. Согласовать с существующим `content_admin` единый порядок locks (`hierarchy` перед `studio` при необходимости обоих), не брать их в обратном порядке. Устаревший клиент получает конфликт без перезаписи. Предложить загрузить серверную редакцию, скачать свою или сохранить обе отдельными проектами. Существующий runtime import не идемпотентен: каждый вызов создаёт новую активность. Требуется дедупликация по contentid + sourceversion + package hash: повтор возвращает результат, другой hash для уже зафиксированной редакции отклоняется. Создание и отправка в каталог имеют request token/idempotency: повтор запроса после таймаута не создаёт дубликат материала/активности. Нельзя считать несколько независимых save/upload/import вызовов атомарной операцией; нужен явно возобновляемый publication command с фиксацией стадий.

Локальный аварийный черновик привязан к installation ID, реальному Moodle user и project ID. Он не источник общей синхронизации, не переносится между аккаунтами и не создаёт автоматический seed всех RC-курсов. При выходе/отзыве доступа остановить синхронизацию и не показывать кэш другого пользователя.

## Импорт: точный контракт

В исходном `model.js` подтверждены:

| Вход | Результат |
|---|---|
| `.rcproject`, `.rcworkspace`, schemaVersion 1 | Полное редактирование с ресурсами, совместимость сохранить |
| SCORM с `editor.json` формата `ustar-rc-embedded-project` | Восстановление редактируемого проекта |
| Старый USTAR SCORM с JSON-присваиванием `window.COURSE` в `data.js` | Разбор данных без исполнения JavaScript |
| Произвольный сторонний SCORM | Не обещать визуальное редактирование; штатный импорт готового пакета в материалы |
| DOCX/PPTX/PDF | Автоматическое преобразование не входит в данный перенос |

Новые курсы любых подразделений поддерживаются независимо от кода RC. Для чужого SCORM честно показывать ограничение, не пересобирать неизвестный пакет с потерей логики. Новые экспорты содержат editor.json для обратного редактирования. Старые проекты не переименовываются автоматически.

Лимит публикуемого ZIP согласовать с текущим backend: 100 МБ, хотя старый клиент допускает 300 МБ. Показывать эффективный серверный лимит в UI и проверять до отправки; не увеличивать PHP/proxy лимиты без измерений. Ресурсы и импорт workspace передавать частями с отдельными квотами, не giant base64 POST.

Защита импорта нужна на сервере, клиентской regex-проверки недостаточно: лимиты распакованных байтов/файлов/глубины, запрет traversal, symlink, неоднозначных имён, исполняемых вложений исходника; MIME/signature для изображений и шрифтов, whitelist HTML/CSS. Не выполнять загруженные data.js. Preview изолирован; никакого активного импортированного HTML в привилегированном origin без очистки. Не разрешать произвольные внешние URL ресурсов, способные вынести данные за контур.

## Проверки и критерии приёмки

1. Реальный текущий RC-проект: импорт → правка текста/таблицы/фото/шрифта → сохранение → другой аккаунт автора/браузер → совпадают данные и ресурсы. Закрытие вкладки и восстановление после сетевого сбоя.
2. Два автора редактируют одну ревизию: второй save получает конфликт; обе версии можно сохранить; отложенный ответ не стирает более свежие правки.
3. Новый курс другого подразделения и копия проекта; папка/аудитория не расширяются при сохранении. Read-only HR, обычный сотрудник, suspended и view-as не получают author write/file access.
4. Совместимые ZIP/project/workspace проходят round-trip. Неизвестный SCORM отклоняется только для редактирования, с переходом к штатному импорту. Некорректные архивы/HTML/ресурсы безопасно отклоняются без частичных материалов.
5. Save-to-material повторяется после таймаута без дубликатов. Сбой сборки оставляет восстановимый черновик и точный статус, не сообщение «готово».
6. SCORM работает без внешних запросов в изолированной копии Moodle: запуск, картинки/шрифты, resume, завершение, evidence и маршрут. Новый пакет не удаляет старые попытки/активности.
7. Визуальное сравнение с исходником desktop/mobile: панели, toolbar, свойства, preview, без переполнений и пересечений с темой.
8. PHP/JS/source contracts + Moodle DB integration tests, затем полный release gate проекта. Результаты каждого уровня фиксируются отдельно; production acceptance остаётся отдельным шагом владельца.

## Что ещё необходимо проверить

Личные последние правки исходного сайта не получены: стартовый seed не равен синхронизированным пользовательским версиям. Для миграции использовать «Скачать все проекты» из актуальной пользовательской сессии и загрузить workspace в новую студию. Не обращаться к чужому ChatGPT account storage.

Перед разработкой нужен выбор этого решения и согласование границы «совместимые проекты редактируем, произвольный SCORM импортируем готовым». После согласования — детальный implementation plan, реализация в отдельной ветке, проверки, PR и точные инструкции установки. Этот документ не является готовым релизом.
