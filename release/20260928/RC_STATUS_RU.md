# USTAR: подготовка единого релиз-кандидата

Статус: **черновая интеграция, установка в production запрещена до закрытия ворот ниже**.
Точный SHA определяет release manifest успешного полного CI, а не название PR.

## Проверенная исходная база

- Последний подтверждённый владельцем production source: `0e1eba2ca08b11f929730ab09df7bc91732f0e62`. Read-only manifest от 27.09: 424 совпавших файла, без изменений, лишних или недостающих файлов. Версии DB `local_ustar=2026092601`, `theme_ustar=2026092601`.
- База должна быть заново сравнена с сервером перед установкой. Этот снимок не охватывает БД, moodledata, конфигурацию и возможные последующие изменения на сервере.
- Последовательный стек после production PR №16 проходит через интеграционный PR №32 и последующие PR до актуального head. Отдельные черновые PR не устанавливаются по одному и не считаются принятыми.

## Что вошло в исходники

Пакеты G01–G06: контракты прав и файлов, регистрация и уведомления, задачи, модель должности, грейды и Лента. Далее: переносимый вводный блок, пакетные чтения и пагинация, защита CLI, блокировки материала, оформление Ленты, миграция прав, объединённый центр уведомлений, чтение маршрута без доменных записей, явная синхронизация результата и одинаковый допуск при прямом запуске. Последний пакет выравнивает блокировку создания точки и версии и различает ошибку загрузки маршрута и отсутствие настройки.

Это перечень исходного кода, **не подтверждение сквозной работы**.

## Ворота до признания RC

Диагностический полный run №308 на родительском PR №47 прошёл source/frontend/rollback/prepare-rc, но остановился до upgrade: fixture старого Boards пытался сеять таблицу, уже удалённую в подтверждённом production baseline `2026092601`. Тестовый harness теперь различает исходную систему до retirement и уже архивированную базу. Этот run **не** является успешным Moodle DB доказательством; нужен повторный полный gate на новом SHA.

Run №313 на PR №48 прошёл source/frontend/rollback/prepare-rc, обновление с production baseline и его повтор, затем остановился на побайтовом сравнении JSON-снимков схемы. У схем совпали все таблицы, столбцы, свойства и индексы; отличался только порядок столбцов в JSON: upgrade добавляет поля в конец, чистая установка следует порядку install.xml. Снимок теперь сортирует столбцы по имени. PHPUnit ещё не запускался; новый полный gate обязателен.

Run №315 прошёл source/frontend/rollback/prepare-rc, обновление, повторное обновление и сравнение с чистой установкой. PHPUnit выполнил 115 тестов и выявил один дефект отказа публикации точки внутри внешней транзакции и одну отсутствующую локализацию capability Ленты. Публикация пустого шага теперь отвергается до вставки точки; строки всех заявленных capabilities добавлены в en/ru. Нужен новый полный gate на следующем SHA.

1. Зафиксировать один Git SHA и выполнить на нём `source`, `frontend`, `rollback`, `prepare-rc`, `moodle-db`, `gate` без пропусков. Сохранить manifest, журнал upgrade, parity свежей установки, повторного upgrade, PHPUnit и отката.
2. Сверить 8 новых требований, все 60 audit ID и 13 старых замечаний: для каждого указать код, доказательство, статус приёмки или явное исключение по решению владельца. Старый реестр датирован 24.09 и не описывает все последующие PR; отсутствие обновления не доказывает отсутствие кода.
3. Проверить реальный состав шести опубликованных вводных шагов read-only CLI, зависимости и доступ к курсам/материалам для склада и другой целевой должности. Копирование шести черновиков в исходниках само по себе не публикует маршрут и не зачисляет людей.
4. Пройти браузерную UX-сверку USTAR на финальном SHA: сотрудник, руководитель, HR/HRD, администратор; регистрация → назначение → маршрут → подтверждение → переобучение → грейд; материалы, задачи, Лента, поиск, пустые и ошибочные состояния, клавиатура и ширины 360/768/1280/1920.
5. До установки выполнить новый read-only production manifest, сверку версий и кадровых конфликтов; подготовить проверенный комплект DB + moodledata + source + config, план миграции прав и восстановление. Нельзя понижать plugin DB version простым откатом файлов.
6. После выпуска владельцем отдельно проверить production smoke и скорость на согласованном объёме. Изолированный CI не воспроизводит его реальные кадровые данные, старые уведомления и файлы.

## Осознанные границы продукта

- Полный Moodle Privacy API отложен владельцем, если не блокирует обучение и функционирование. Утверждённые сроки хранения Ленты документируются; автоматическое удаление выключено.
- Bitrix в текущем коде получает `disabled` для новых событий: рабочего внешнего адаптера нет. Старые `pending` не меняются без сверки серверной интеграции. Не объявлять внешнюю доставку работающей.
- Штатное планирование будущих дат, полный общий gate evaluator и другие неиспользуемые/неблокирующие расширения не объявляются реализованными только ради этой поставки. Их включение требует отдельного кода и приёмки.

Ни один пункт в этом документе не разрешает слепое копирование файлов или автоматическую кадровую миграцию.
