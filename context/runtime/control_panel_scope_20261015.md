## Продуктовый контракт

Один интерфейс на русском для desktop и телефона. Главный экран отвечает: работает ли Академия, защищены ли данные, какое действие нужно владельцу. Верхние карточки: Академия / Сервер / Бэкапы / Требует внимания. Цвет сопровождается текстом и временем последней проверки. Неизвестно, устарело, обслуживание и авария — разные состояния; отсутствие метрик не зелёный статус. Время показывать в Europe/Moscow с явным часовым поясом, хранить UTC. Важная информация видна без перехода к техническим графикам.

| Раздел | Содержимое и смысл |
|---|---|
| Обзор | Доступность и задержка, свежесть данных, текущий инцидент, последний успешный backup, последний подтверждённый restore, следующая операция |
| Сервер | CPU, RAM/swap, filesystem bytes/inodes, диски/SMART и тренды, контейнеры/службы, uptime, температура при наличии датчика; общий хост включает нужные mail/DNS службы |
| Академия | Web/БД, cron и результаты задач, возраст очереди, новые ошибки, версии core/plugin/image, maintenance; не считать HTTP200 доказательством полного пользовательского сценария |
| Бэкапы | Расписание, список/размер/место хранения/срок, создание, checksum/decrypt/restore как отдельные проверки, SSD archive отдельно; независимая копия и ключ отдельно от backup на том же хосте |
| Алерты | Новые/признанные/устранённые, серьёзность, причина, время, затронутый компонент, понятное действие, доставка/повторы/восстановление |
| Операции | Фиксированные команды, этапы/результат/длительность/исполнитель, блокировки, технические подробности по раскрытию; история после закрытия браузера |

Не создавать второй магазин пользователей/ролей/прогресса. Пульт наблюдает backend и выполняет эксплуатационные операции через узкий контракт. Учебные и кадровые изменения остаются в Moodle/USTAR.

## Границы реализации

Пульт логически независим от Moodle, чтобы отказ Moodle не закрывал управление. Для полной потери server1 нужен независимый наблюдатель. Предпочтительное размещение пульта вне server1 уточняется по наличию отдельного узла и домена; никакой VPS не закуплен и внешние учётные записи не созданы. В первой версии можно работать с локальными данными/контрактами без доступа извне, но обещание внешней доступности закрывается только проверкой с другой сети.

Browser → аутентифицированный API пульта → ограниченный агент server1. Интерфейс не получает Docker socket, shell или DB superuser. Данные телеметрии не содержат env/passwords/config/dumps и персональных labels. Требования доступа: HTTPS, персональные учётки, MFA, разделение просмотра и операций, отзыв сессий. Конкретный способ защищённого соединения и auth выбирается после проверки сети/отдельного хоста.

Операции первой поставки: обновить статус, создать Moodle backup, проверить выбранный архив, подготовить тест восстановления, остановить принадлежащий пульту стенд, получить обезличенный отчёт. Backup показывает предстоящую краткую паузу web и получает явное подтверждение запуска; repeated click не создаёт вторую операцию. Проверенные существующие scripts используются через adapter, не переписываются ради UI. Restore тест запускается только после готовности пульта по текущему решению владельца. Production restore/update/reboot — отдельные подготовленные операции с последствиями и подтверждением; произвольного терминала, автоудаления архивов и автоматического ремонта нет.

## Источники и алерты

Уже реализованы HDD timer/status/last-hdd-success/sidecars и private cron reports; новые сборщики должны учитывать их реальные schemas/версии. Только чтение статуса не должно запускать backup/cron/PHP bootstrap. Host/container metrics собираются ограниченным агентом с фиксированными командами; DB aggregation отдельной read-only учёткой и timeout. Текущее наличие общего collectors/alert delivery не подтверждено.

Первые алерты: Академия недоступна; нет heartbeat server1; backup не завершился в ожидаемое окно; checksum failed; HDD отсутствует; low space/inodes; новые cron/task failures; устаревшие/пропавшие метрики; зависшая операция. Порог задержек и ресурса калибруется по наблюдениям, окно обслуживания ограничено по времени. Исторические2 failed/18 overdue задачи из owner status нельзя каждый раз выдавать за новую аварию. Дедупликация, группировка, уведомление об устранении и неисправности доставки обязательны. Telegram ранее предпочтён владельцем; получатель, ключи и отправка тестового сообщения ещё не настроены/не выполнены. Падение пульта не должно отключать внешний контроль/алерт.

## Последовательность и критерий готовности

1. Зафиксировать состав, UX и data/action contracts; уточнить отдельный узел и домен.
2. Подготовить адаптивный интерфейс с явно демонстрационными данными, включая stale/error/loading/maintenance, не изображая live server.
3. Подключить read-only метрики и архивы, auth/HTTPS и проверку извне. Проверить малую нагрузку и бюджет хранения.
4. Подключить алерты/доставку с согласованным получателем и контролируемыми отказами; проверить dedup/recovery/lost heartbeat.
5. Подключить ограниченные операции и аудит: повторный клик, отсутствие прав, занятый lock, потеря соединения, failure/resume без двойного запуска.
6. Из принятого пульта запустить отложенный restore на час; проверить архив/DB/файлы/роли/SCORM и автоостановку. Другой чистый сервер — отдельная off-host приёмка.
7. Вернуться к Moodle5.3/PG17 с сохранённой подготовкой PR101.
