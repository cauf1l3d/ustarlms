## Открытые блокеры

### Материалы и результаты: assessment замкнут, Studio SCORM feature-gated

На текущем head Studio Assessment подключён к каноническому маршруту: learner
projection не содержит правильных ответов, preview не пишет учебный результат,
повтор одной сдачи идемпотентен, а route requirement принимает только сохранённый
PASS именно текущей source-version. После route reconciliation создаются обычные
`route_progress` и `completion_cycle`, поэтому дальнейшие Evidence/reward/grade
механики используют существующий единый контракт, а не отдельный результат Studio.

Опубликованный source теперь нельзя менять на лету: автор обязан вернуть материал
в draft, сохранить новую source-version и опубликовать снова. Старый PASS не
закрывает новую source-version.

Полноценный runtime импортированного Studio SCORM ZIP (launch/resume/score/completion)
в этот RC не входит. Это не скрывается как работающая функция: сервер запрещает
публиковать Studio SCORM как завершаемый route requirement. Для production RC
поддерживается существующий Moodle SCORM через requirement `type=cm` и USTAR
SCORM launcher, где уже используются Moodle completion и SCORM completion status.
Studio SCORM runtime переносится в post-release backlog и не является production
capability этого кандидата. Перед снятием draft остаётся браузерный smoke Studio
Assessment и Moodle SCORM на точном RC SHA.

### Грейды: кодовый P1 закрыт, остаётся приёмка

На текущем head переходы грейдов используют отдельные опубликованные immutable-правила
`grade_rules` для конкретной пары from/to и должности. Правило фиксирует точные
опубликованные версии точек маршрута; заявка сохраняет snapshot rule id/version/hash,
а решение повторно сверяет актуальную ступень, правило и фактического текущего
руководителя. `reconcile()` создаёт заявку автоматически только после выполнения
явно опубликованного правила; отсутствие руководителя блокирует создание.

Тесты подтверждают версионирование правил, запрет точки из чужого маршрута и то,
что правило соседнего перехода не переиспользуется неявно. До RC остаётся
браузерная/ролевая приёмка смены должности и руководителя, отсутствие руководителя,
повторное решение и конкурентный сценарий; бизнес-критерии каждого перехода должны
быть опубликованы владельцем процесса через экран правил, а не выведены системой.

### Production acceptance и восстановление

CI устанавливает исторический код на синтетическую БД и проверяет seeded upgrade,
включая обычную и soft-deleted доски, архив, повторный upgrade и rollback-drill
в изолированном CI. Это остаётся автоматическим migration gate.

Для этого выпуска выбран production-smoke подход вместо отдельного restore rehearsal:
до применения точного RC обязательны maintenance mode, остановка writers/cron,
согласованный backup PostgreSQL + moodledata + code и manifest preflight. На
production разрешён только контролируемый функциональный smoke на выделенных
тестовых пользователях и read-only сверка существующей истории. Destructive
migration experiments, downgrade и rollback-drill на рабочей системе не выполняются.

Это оставляет больший residual risk, чем отдельная репетиция на восстановленной
копии, поэтому первый schema/data mismatch, потеря связей, двойной completion/reward
или нарушение scope является STOP/rollback. Откат — восстановление DB + moodledata
+ code одной точки; уменьшение version.php или запуск старого кода на новой схеме
запрещены. Точный порядок зафиксирован в
`context/runtime/production_rc_20260922.md`.

### P2: задачи и UX

Редактирование/удаление блокнота, сроки и результат поручений добавлены в PR #11.
Остаются сквозные связи с исходными процессами и браузерная приёмка.
Вкладка чек-листов сама по себе не доказывает интеграцию сервиса. Проверить владельца при подмене
ID, view-as, API, экспортах; заметки не должны попадать в общие журналы.
Проверить мобильную навигацию, подписи полей, сохранение ввода при ошибке,
понятные ошибки отправки аттестации, SCSS в реальном Moodle браузере.

### P2: инженерная устойчивость

- Проверить HTTP загрузки и восстановление старых File API ссылок при сбое;
  успешный unit test без реальной загрузки не закрывает этот сценарий.
- Проверить уведомления при параллельной доставке и сбоях хранилища: общая
  функция больше не скрывает ошибки, но многопроцессный сценарий ещё не измерен.
- Несколько выборок не ограничены и вызывают дополнительные запросы на строку:
  pending grade requests, tasks, board archive migration. Измерить на реалистичном
  объёме, затем вводить пагинацию/пакетность с сохранением корректности.
- Проверить гонки на границах внешних транзакций, фактическую единственность
  старых completion cycles и уже начисленные rewards до смены identity policy.

## Порядок единого применения

1. Закрыть открытые P1, выполнить ролевую/браузерную приёмку. Зафиксировать один
   immutable commit кандидата и проверить именно его CI, а не CI предыдущего head.
2. Из CI сохранить source archive и release-manifest.json. Manifest содержит
   точный baseline и план удаления; hashes сверять перед любым изменением.
3. Выполнить production_manifest.py --require-match на актуальной установке.
   Drift, непрочитанные файлы, символические ссылки, неизвестный baseline — стоп.
4. Перед production включить maintenance mode, остановить writers/cron и
   сохранить согласованный backup PostgreSQL + moodledata + code. Зафиксировать
   точный RC SHA и pre-deploy counts/hashes для критичных доменов.
5. Применить один пакет только в пределах local/ustar и theme/ustar; удалить
   только перечисленные и совпавшие со старыми хешами файлы. Moodle core не менять.
6. Выполнить Moodle upgrade и очистку caches, сверить итоговый manifest.
7. Не снимая maintenance mode, выполнить технический и ролевой smoke на выделенных
   тестовых пользователях по `context/runtime/production_rc_20260922.md`, затем
   read-only сверить существующие progress/Evidence/Economy/materials.
8. Только после зелёного smoke включить workers/cron и снять maintenance mode.
   При провале gate восстановить согласованную точку целиком; частично обновлённую
   схему в эксплуатацию не вводить.

Production deployment разрешается только для замороженного immutable RC SHA с
зелёным CI и успешным manifest preflight. Сам deploy не считается приёмкой:
maintenance mode снимается только после production smoke и read-only сверки по
runbook. До этого PR остаётся release candidate, а не подтверждённый production release.
