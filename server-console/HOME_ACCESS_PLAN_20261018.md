# Домашний доступ с сохранением основной сети — решение18Oct

Статус: **проект следующего этапа, ничего не установлено**. Последнее требование владельца: сохранить интернет/LAN на домашнем Windows ПК и server1, не менять корпоративный router/VPN и не открывать входящие порты. Ранее Tailscale на другом VPS нарушал доступность домашней сети; точная причина неизвестна. Нельзя переносить тот опыт в диагноз текущей сети.

## Xray и Happ

Подготовленный для Telegram Xray — исходящий клиент сторонней VLESS подписки, loopback HTTP proxy и default deny. Он не делает server1 доступным из интернета, а Happ с той же подпиской подключится к узлу провайдера, не к server1. Чужая подписка не даёт управления портами/reverse endpoint на узле провайдера.

Технически Xray умеет reverse bridge/portal. Server1 может установить исходящий туннель к **своему управляемому внешнему узлу**, через который домашний клиент получит доступ к выбранному сервису. Нужны конфигурация/аутентификация/ограничения с обеих сторон; одного профиля Happ недостаточно. Это отдельный маршрут и отдельная служба, не расширение Telegram-only allowlist. Внешнего управляемого узла для этой задачи пока не подтверждено.

## Кандидат: Tailscale userspace и обычный SSH

Выбран для проверки минимальный TCP-доступ к самому серверу. Старое предложение subnet route192.168.1.60/32 **отменено как текущий план**: оно требует маршрутизации/IP forwarding и не отвечает новому ограничению. Оно остаётся только историей решения до этой команды владельца.

На Linux рассмотреть отдельный daemon с `--tun=userspace-networking`, своим state/socket и непривилегированным пользователем. Он не создаёт TUN/interface и не получает NET_ADMIN, не устанавливает routes/netfilter и не меняет DNS. Не объявлять/не принимать subnet routes и exit nodes; MagicDNS/accept-DNS выключить. No Funnel, никакой публикации в интернет. Restrictive grants должны быть установлены до выдачи доступа: только назначенное домашнее устройство/владелец к server node TCP2222, без прежнего широкого default allow. Это не готовая конфигурация и не native acceptance.

Сторона сервера предоставляет только один TCP forwarder через Tailscale Serve к существующему OpenSSH22. Приёмка проверяет, что обычный sshd доступен с локального адреса и forward действительно работает в выбранной версии userspace. Парольный/root доступ дополнительно не открывать: отдельный SSH ключ, проверка host key, текущий пользователь/права ОС. SFTP/VS Code Remote SSH идут через тот же SSH. Tailnet identity не заменяет SSH authentication.

Домашняя сторона при строгом требовании «без изменения сети» тоже требует userspace/app-specific транспорта: например `tailscale nc` как SSH ProxyCommand либо loopback SOCKS для одного приложения. **Обычный Windows GUI клиент добавляет виртуальный адаптер и системные маршруты**; выключенные exit node/accept-DNS/accept-routes не означают полного отсутствия сетевых изменений. Его установку не предлагать как гарантию «ничего не сломает».

Запуск Windows userspace daemon и его жизненный цикл должны быть сначала проверены на Windows в изоляции: штатный GUI не предоставляет этот сценарий как простой переключатель. Альтернатива — уже существующая Linux VM/WSL; установка новой VM/WSL сама меняет Windows networking и не является скрытой безопасной заменой. Если выбранный Windows build не даст изолированный режим, согласовать явно ограниченное добавление адаптера либо использовать свой relay/SSH reverse tunnel; не ослаблять требование молча. Сейчас ни одна домашняя конфигурация не выдана как проверенная.

Пульт сохраняет origin/cert на192.168.1.60:8443. Просто открыть тот же сервис по100.x нельзя: Host/Origin/cert не совпадут. Через SSH можно организовать proxy только отдельного браузерного профиля к прежнему LAN origin с прежним CA; либо отдельно проектировать второй origin/сертификат. Не менять wwwroot Академии, не отключать TLS/Host/Origin проверки ради VPN.

## Проверка перед установкой и откат

1. На обоих концах сохранить локально adapters/routes/default gateways/DNS/proxy/firewall и сетевые проверки. На server1 также IPv4/IPv6 routes, Docker networks, listeners и критические сервисы. Снимки не публиковать целиком.
2. Сначала проверить исходящую доступность coordination/DERP с обоих концов; обычно port forwarding не требуется, но запрещённый egress всё равно не обходится одной установкой. Telegram-only18081 не подходит для Tailscale: его allowlist не расширять.
3. Проверить official pinned binaries и тестовый daemon отдельно от production: no TUN/NET_ADMIN, открытые назначения ограничены, TCP2222 разрешён нужному устройству, посторонний узел/порт отклоняется. Для host/Internet connection lifecycle задать bounded ресурсы и автоматический останов теста.
4. На server1 первый запуск только временной отдельной службы с auto-stop, при сохранённом текущем SSH сеансе. Проверить SSH/SFTP, Интернет/DNS/LAN/Академию с существующих устройств до/после, отрицательные grants, останов/повторный старт. Аналогично проверить домашний ПК и его LAN/параллельный Happ.
5. Сравнить baseline после запуска и после stop. При userspace никакой правки default routes/DNS/netfilter не ожидается. При изменениях или потере доступности — остановить новую службу, не «чинить» общий firewall/router; разобраться до постоянного включения.
6. Откат: останов/disable только новой службы, revoke node в tailnet, после проверки удалить только её state/binaries/unit. Не выполнять iptables/nft flush, netplan apply, сетевые restart или пакетный purge существующего сетевого стека. Постоянное включение — после нативной приёмки, без абсолютного обещания отсутствия сбоев.

Область доступа — администрирование server1. Связь со всей корпоративной LAN, RDP и широкие subnet routes в этот первый этап не входят. Уже имеющиеся полномочия интерактивного SSH пользователя остаются полномочиями ОС; Tailscale grant не ограничивает действия пользователя внутри SSH.
