**Метод:** сверка исходного аудита, GitHub, датированных серверных свидетельств и выводов команд владельца 03–06.10, результатов копирования/восстановления/cron и официальной документации. Сохранена структура исходного документа; изменены текущие статусы, требования платформы и порядок работ.

**Граница достоверности:** прямого подключения аудитора к production нет. Факты сервера — предоставленные владельцем результаты, а не непрерывное наблюдение. Последний результат операции хранения получен 06.10 в 09:06 UTC: `GPT_COPY_READBACK=PASS`. Более позднего подтверждения записи GPT, расширения раздела или файловой системы не предоставлено. Нагрузочный тест, полный пентест и восстановление всего общего сервера на чистое оборудование не выполнены.

**Согласованная последовательность:** распоряжение владельца 06.10 заменило прежнее «регулярные копии в финале»: **хранение и карта сервера → начальная автоматизация копий на HDD → отдельный стенд → Moodle/CI/ОС → HTTPS**. Остальные вопросы остаются в плане; рекомендации аудита сами по себе не меняют эту последовательность.

**Статусы:** **сделано** — конкретная операция подтверждена; **частично** — часть приёмки ещё впереди; **подготовлено** — есть проверенный код/команда, но нет результата на сервере; **осталось** — работа не выполнена; **не проверено** — достоверных данных недостаточно. Приоритет риска и статус выполнения — разные вещи. Успешный CI не равен production-приёмке, успешный checksum не равен восстановлению, установленный timer не равен успешному ночному запуску.

## 1. Итоговое резюме (TL;DR)

**Сейчас мы на этапе подготовки хранения общего сервера к дальнейшим обновлениям.** Cron Академии восстановлен. HDD проверен в согласованном объёме, размечен, подключён и используется для зашифрованных копий; свежая ручная копия и ежедневный timer подтверждены. Сохранена таблица разделов и загрузочные области SSD. **Сам SSD ещё не расширен: следующий шаг — исправить положение резервной GPT, затем отдельно увеличить корневой раздел и ext4.** Новый стенд и обновление production ещё не выполнены.

Академия доступна сотрудникам по **HTTP внутри корпоративной сети**, отдельный Next.js frontend не используется. В компании 60–70 человек, в пилоте около 18; планируется 200 и дальнейшая B2B-продажа. Эти числа описывают аудиторию, а не доказанную одновременную нагрузку. Почта, DNS и ISPConfig на этом же сервере нужны и входят в проверку последствий каждой инфраструктурной операции.

После хранения возвращаемся к стенду; второй cron, удаление лаборатории и перенос работающих каталогов для этого не требуются.

Открытые риски не скрыты установленным timer: права приложения, HTTP, отсутствие общего мониторинга, старый production patch, непроверенное полное восстановление хоста и остаточное состояние HDD сохраняются. Общий процент «аудит выполнен» не присвоен: этапы имеют разные критерии приёмки.

## 3. Что сделано хорошо (важно не сломать)

**Границы приложения:** бизнес-логика в local_ustar, тема — представление, существующие сервисы — единый источник данных. Не создавать вторую БД сотрудников/грейдов/чатов для нового клиента. Обнаруженный redirect core index — отдельное фактическое исключение, которое нужно учесть при выпуске.

**Воспроизводимость и свидетельства:** immutable application SHA, пары версий, manifest, release ledger, fresh/upgrade/repeat tests и rollback CI. При этом CI, публикация контекста и действие владельца на сервере имеют разные статусы. В Git не опубликованы конфигурация с секретами, архивы, приватные журналы и сырой boot-copy.

**Рабочий cron:** один worker, блокировки, результат прохода и задачи, закрытые журналы и согласование с backup. Второй планировщик не нужен. Исторические ошибки сохранены, H5P failure не скрыта нулевым exit процесса.

**Резервирование развивается проверяемыми шагами:** исторический encrypted archive и isolated restore; свежий HDD trial с checksum/readback и возобновлением Moodle; timer без catch-up, автоудаления и тихого fallback на SSD. Это полезные ограничения, но full DR ещё не доказан.

**Изменения storage пока отделены:** raw GPT/boot copy сделана до записи; relocation не объединена с growpart/resize/reboot. Сохранены границы общего хоста. Блокировки команд защищают только от согласованно использующих их процессов, а не от любых действий другого администратора.

**Серверные проверки назначения выполнены read-only:** 72 аккаунта, 71 ready и 1 position_missing; to_enrol=0, missing_manual=0, исключений нет. Legacy-position защищённой учётки Академии не исправлялась автоматически. Это не пропущенный кадровый перевод, который можно менять ради нулевого счётчика.

Реальный полный host disaster recovery пока не испытан. | ОС | Обслуживание Ubuntu 24.04, AppArmor и плановый reboot не подтверждены; release-upgrade ОС не запускался |
| Future LTS | 5.3 стабилен, но переход ещё не спроектирован/не выполнен; нужен PG 17+ |

[PHP 8.3](https://www.php.net/supported-versions.php) получает security support до 31.12.2027; 8.2 — до 31.12.2026. Это календарь веток, не проверка актуальности production image. [PostgreSQL 16](https://www.postgresql.org/support/versioning/) поддерживается до 09.11.2028; 16.15 — текущий опубликованный minor на дату сверки. Поддержка PG16 не отменяет несовместимость с минимальным требованием Moodle5.3.

Текущий выбранный порядок сохраняется: сначала stage и patch5.1.8/CI/OS, затем HTTPS; major/LTS — отдельный проект. Общий host требует post-check почты/DNS/ISPConfig после пакетов и reboot. Не менять Moodle, PG major, Apache и permissions одной непроверяемой операцией.

### 5.2. Privacy API не реализован — технический пробел и отдельная политика данных

В baseline нет `local/ustar/classes/privacy/provider.php`; существует privacy inventory прямых ссылок на людей. По [Moodle Privacy API](https://moodledev.io/docs/5.1/apis/subsystems/privacy) компонент с собственными персональными данными должен описывать обработку и поддерживать нужные операции; null-provider не подходит вместо реального provider.

**Осталось / отложено отдельным этапом:** согласовать экспорт, удаление/обезличивание, retention и исключения для evidence/кадровой истории; реализовать metadata/export/deletion и проверить связи/файлы/права на копии. Не все 93 таблицы объявлены персональными; юридическое соответствие конкретному закону этим техническим аудитом не установлено. Нельзя удалять учебную историю без согласованной политики. До B2B-поставки техническая и организационная части должны пройти отдельную приёмку.

### 5.3. Управление уязвимостями и канал security-отчётов

Постоянный эксплуатационный контур обновлений/advisories, ответственный, канал security-отчётов и сроки реакции не подтверждены как внедрённые. Файлы политики/зависимостей в Git и GitHub security features — разные механизмы; отсутствие dependabot.yml не доказывает отсутствие всех GitHub-проверок. CI/npm audit не покрывает OS, Moodle, PHP/PG images и production-конфигурацию полностью.

Нужно закрепить ответственность, источники advisory, exact-version inventory, процесс tested patch/rollback и применимую автоматизацию dependency PR без автодеплоя. MFA/SSH/firewall вводятся после проверки effective policy, исключений и аварийного доступа. Отключённые factor_grace/nosetup не доказывают, что вся MFA выключена. Нельзя потерять текущий канал управления при усилении доступа.

### 5.4. Второй frontend и будущая B2B-модель — разные задачи

Next.js frontend сохранён в исходниках, но не используется в production. Его наличие не требует запускать второй UI и не закрывает запрос Android/iOS. Mobile должен использовать существующую серверную модель, единые права, evidence, грейды, сообщения и ledger. API inventory, auth/revocation/files/offline/idempotency, ADR, клиент и устройства — отдельные невыполненные этапы; PWA не объявлена полным мобильным приложением.

B2B-модель ещё не выбрана. 200 пользователей одной компании и изолированные данные разных компаний — разные задачи. Возможны отдельные установки либо доказанная tenant isolation; наличие подразделений и ролей не доказывает второе.

| B2B-критерий | Что нужно подтвердить до клиентского production |
|---|---|
| Изоляция | Данные, файлы, caches, задачи, токены, экспорт и admin-access каждой компании |
| Поставка | Версионированная установка, конфигурация вне кода, upgrades и client compatibility |
| Эксплуатация | Мониторинг инсталляций, аудит поддержки, SLA/RPO/RTO, инциденты |
| Recovery | Restore одной компании без потери/раскрытия другой |
| Безопасность и данные | ACL/IDOR/files, secret management, HTTPS, retention/export/delete, требования обработки данных |
| Лицензии | Проверка условий Moodle, темы, зависимостей и выбранного способа распространения |
| Ёмкость | Реалистичные сценарии и joint load, quotas по медиа/фоновой работе |

Это планируемые критерии. Kubernetes/микросервисы/переписывание приложения из цели B2B автоматически не следуют.

### 5.5. Управляемый технический долг

**Миграции:** не обрезать upgrade.php и историю. Fresh install использует install.xml/install.php; утверждение, что он обязательно прогоняет всю историю upgrade, неверно. Нужны XMLDB parity, fresh/upgrade/repeat и реальные compatibility paths, включая старые версии.

**Большие классы и страницы:** размер файла сам по себе не обосновывает рефакторинг. Сначала дефект/профиль, затем ограниченное изменение с доменными контрактами. Общие источники employees/completion/wallet/chat сохраняются.

**Интеграции:** внешняя доступность, endpoints, secrets и фактическое использование проверяются отдельно. Историческое наличие Bitrix/IntelliBoard/BBB не разрешает отключить действующие компоненты; новая Bitrix-интеграция отложена. API и provider inventory нельзя считать испытанием сетевой доставки.

## 6. Производительность и ёмкость: пилот 18 человек → 60–70 сотрудников → 200 и далее

**Нагрузочная пригодность не аттестована.** Спокойный CPU/RAM-снимок и маленькая логическая БД не доказывают p95, поддержку 200 одновременно активных сотрудников и будущую совместную B2B-нагрузку. Сначала сценарии/одновременность/допустимая latency и объём медиа; потом тест на stage и сравнение с наблюдаемым production.

| Зона | Известно | Следующая проверка |
|---|---|---|
| PHP/OPcache | CLI settings ранее enable=On, memory=256, max scripts=20000 | Эффективный web SAPI/cache, hit/miss/restarts/memory; CLI status=false не доказывает выключенный web cache |
| PHP concurrency | Container Apache/PHP | Active/queued workers, RAM/process, latency, saturation; workers не увеличивать вслепую |
| PostgreSQL | Исторический logical104MB; 100 connections, 128MiB shared buffers, 4MiB work_mem | Connections/locks/slow SQL/autovacuum/p95; work_mem умножается параллельными операциями |
| MUC/сессии | Moodle/session/cache используются | Реальные stores/locks/latency; Redis — возможное решение после измерения, не обязательная установка |
| Cron | Один worker, backlog очищен; внешние exceptions известны | Дневной/ночной duty cycle, очереди/age, медленные задачи, влияние backup/контента |
| Storage | Root78%, около61,79GiB хвоста SSD; HDD451G available | Завершить безопасное расширение, budget stage/releases/logs/backups и темп роста |
| Медиа/сеть | Файлы, SCORM/H5P, чат | Размеры/частота, streaming/download concurrency, сеть LAN и burst I/O |
| Другие службы | Почта/DNS/ISPConfig нужны | Их latency/очереди во время backup/load/обслуживания Академии |

Приёмка PERF-01: согласованные реальные сценарии нескольких ролей, замеры p50/p95/p99/errors и ресурсов, сравнение до/после, отсутствие регрессии нужных общих служб. Нагрузочный тест не запускается без оценки влияния на production. Отдельный сервер БД/Redis/центральные логи — решения по измерениям, не обещание устранить все проблемы заранее.

Только SELECT ролей в read-only transaction:

```bash
sudo -n timeout 20s docker exec -e 'PGOPTIONS=-c default_transaction_read_only=on -c statement_timeout=15000 -c lock_timeout=3000' ustar_postgres psql -X -w -v ON_ERROR_STOP=1 -U moodle -d moodle -c 'BEGIN READ ONLY; SELECT rolname, rolsuper, rolcreaterole, rolcreatedb, rolreplication, rolbypassrls FROM pg_roles WHERE rolname=current_user; COMMIT;'
```

PGOPTIONS не гарантирует read-only PHP/Moodle DB driver: раньше это подтвердилось STOP-проверкой. Для прикладного probe нужен явный SET SESSION после bootstrap, проверка current_setting и только заранее изученные методы. Наличие проверки само по себе не разрешает вызывать произвольный изменяющий метод.

### 9Б. Файловый manifest и адресные дополнительные проверки

Использовать известные reviewed helpers с точной версией и областью, а не снова устанавливать wrapper или запускать PHP-файлы из extras. Manifest plugin/theme и core — отдельные сравнения. HTTP200 от login не доказывает успешную авторизацию или работу кадрового сценария; systemctl Result=success без времени/последнего отчёта не доказывает ночной backup.

Команды изменения storage опубликованы в отдельных [GPT-copy](../runtime/ssd_partition_table_copy_20261006.md) и [GPT-relocation](../runtime/ssd_gpt_relocate_20261006.md) runbooks. Copy уже выполнена; её повтор не является текущим шагом. Не объединять relocation/growth/resize и не повторять запись после ошибки без разбора фактического состояния. Здесь аудит, а не разрешение запустить все команды плана одной вставкой.

Полные журналы могут содержать персональные данные/URLs; выводить обезличенные summaries, не пересылать raw logs. Не выполнять upgrade/--install/--tick/cleanup как «проверку статуса».
