# Сброс назначения адаптации — 02.10.2026

База PR75: `79be8529f949cc86164d287c5089f7d4271a9ca5`.
Ветка: `codex/ustar-adaptation-reset-20261002`.
Версии: local_ustar `2026100204`; theme_ustar остаётся `2026100202`.

В HRD → Контроль → Адаптация кнопка «Сбросить назначение» появляется у активного
цикла и цикла на решении HRD: в реестре и открытой истории. Форма требует причину
и подтверждение. Сервис повторно проверяет полномочие manageadaptation, реального
действующего актора и запрет writable view-as. Завершённая адаптация не отменяется.

Сброс отменяет назначение и закрывает его открытые сигналы, сохраняя старые листы,
итоговые отчёты и историю. В истории видны причина, автор и время. Отменённый цикл
не блокирует обучение; повторный POST не дублирует аудит. Старые формы записи
отклоняются. Руководитель может вновь назначить адаптацию через прежнюю кадровую
заявку; это новый ID с чистыми листами, а прежний цикл остаётся в реестре.

Реальный HTTP smoke и сервисные тесты также выявили прежние ошибки адаптации:
для fullname теперь выбираются все native name fields Moodle 5.1; постоянные
ключи дат используют Gregorian ISO в часовом поясе пользователя, без удаления
ведущего нуля display-форматтером. Это позволяет заполнять новый цикл в начале месяца.

Для хранения повторных циклов XMLDB upgrade заменяет только уникальный индекс
staffingrequestid на обычный. Поля и исторические строки не удаляются. Назначение
по одной заявке сериализуется lock; действия внутри цикла используют общий lock
с отменой. Политика описана в ADR 0014. Upgrade сам не сбрасывает адаптации.

Локально проверены diff, shell/JS syntax и структура source/XMLDB. PHP и браузер
в этой среде недоступны; exact-head CI должен пройти до выдачи команды установки.
CI: pre-upgrade история под прежним уникальным индексом, миграция и повторная
миграция, fresh schema parity, unit-регрессии прав/истории/повторного назначения,
реальный authenticated HTTP POST (CSRF, подтверждение, повтор), Chrome 320–1920
и тёмная тема с раскрытой формой. Точные результаты фиксируются в PR.

Installer `scripts/release/deploy_adaptation_reset.sh FULL_REVIEWED_SHA` проверяет
версии PR75 и побайтный исходный manifest, делает согласованный backup БД, кода
и moodledata, затем выполняет upgrade и smoke. На production сами назначения
он не отменяет. После DEPLOY_SUCCESS проверить под HRD кнопку, отмену тестового
назначения и сохранённую историю; под руководителем — новое назначение.
Не использовать для проверки реальное назначение, которое нужно сохранить активным.
Отказ после upgrade требует согласованного восстановления backup, а не только кода.
